# API, Packaging, And Structure Rules

For an SDK the API surface and the packaging around it are product surface, so a defect here compounds in every host. Three families govern that surface: `API` owns dependency direction, package contracts, the public and internal boundary, handle decomposition, release discipline, licensing honesty, and the ban on declared-but-inert surface; `SF` owns package consolidation and naming, on the rule that one package covers one product area with subpath entries per feature; `CS` owns the internal structure of the two oldest packages, `@input/pen-core` and `@input/pen-dom`. `CS` came from a consolidation train that is now closed, so its rules are read as the intended structure of the shipped system rather than as work items — with the exception recorded in CS5, which is not a finished contract.

## API — public API and packaging

- API1. Dependencies point strictly downward and the direction is enforced in CI by `scripts/dag-check.mjs` against an explicit inversion allowlist: `types ← pen-yjs ← core ← extensions`, `core ← dom ← {react, vue}`, and the starter package above everything it assembles. Core depends on nothing above it — anything core needs from a higher layer is either a seam core defines and an extension fills (a facet or a command) or genuinely core and moves in — and no extension depends on a renderer binding, an outward inversion the check treats like any other inverted edge; an extension keeps its framework-free engine and contributes UI through the renderer's own extension surface. The check verifies acyclicity as well as direction and reports a cycle as the package path around the loop, because a cycle stops the build system before it starts rather than stopping one package; `devDependencies` are correctly excluded from the install graph, so a test-only edge from a lower package up to a higher one is a layering inversion the graph cannot see, and the repair is to relocate those tests into the higher package rather than to allowlist the edge. `@input/pen` is the batteries-included entry point — `defaultPreset()` assembling the default schema plus tools, delta-stream, undo, shortcuts, and the HTML clipboard importer, with `createEditor` and `createHeadlessEditor` wrapping core's constructors to default an omitted `preset` to `defaultPreset()`, so a quickstart is one import and `createEditor()`; explicit `preset`, `schema`, and `extensions` options pass through unchanged, and core's own constructors stay the bare path — and package READMEs and docs teach the starter first and core second so core can stay minimal.
- API2. `yjs` is a required `peerDependency` of `@input/pen-yjs` at `^13.6` and `y-protocols` an optional one, both kept as devDependencies for tests, because Yjs is identity-sensitive: `instanceof` checks fail across module copies, and any host doing providers or persistence also depends on Yjs and can silently load a second copy. `y-protocols` is imported only by the `@input/pen-yjs/awareness` subpath, which `@input/pen-multiplayer` depends on, so an install that does not collaborate does not need it; an editor has awareness only when the multiplayer extension ensures it for its scope or the adapter is built with `yjsAdapter({ awareness })`. A second Yjs copy is detected where it can enter: `wrapYjsDocument` throws at creation when the host's `Y.Doc` is not an `instanceof` the adapter's `Doc`, and the first transaction a foreign copy opens on a Pen document — a provider applying updates with its own `applyUpdate` — emits `diagnostic { code: "YJS_SINGLETON_MISMATCH" }` once per document rather than throwing from an observer. React (`^18 || ^19`) and Vue (`^3.4`) stay peers on the same reasoning.
- API3. `@input/pen-types` contains type declarations, frozen constants, pure type guards — a guard is `(x) => x is T` with no allocation and no policy — branded-id constructors (`appId`, `blockId`, `docId`, `zoneId`), and a bounded allowlist of other runtime, nothing else. The creation-time runtime a contract layer must not carry moved to `@input/pen-core`: the schema registry, `defineBlock`, `prop`, and `defineExtension` live in `packages/core/src/schema/` and re-export from core's index, so host-facing API kept working and hosts already have core. The allowlist is what cannot follow them without inverting API1, and today it holds one exported function, `generateId`, required by `@input/pen-yjs`, which sits below core — moving it up would make the adapter depend on core; duplicating it would mint ids from two implementations — plus its private formatter `formatUuidV4`, listed as kind `helper` so unexported helpers cannot hide from the leftover total. CI enforces the boundary (`scripts/types-purity.mjs`): the package declares zero `dependencies`, every runtime export beyond a guard or a branded-id constructor is listed in `scripts/types-runtime-allowlist.json` with a reason, and the gate fails on an unlisted export, a stale entry, an unexported helper missing its `helper` entry, or a source walk that matches nothing. Zero runtime is therefore not the target and chasing it is a regression — the target is that the set stays bounded, justified, and small. The point is that types-only consumers — servers, workers, codegen for other languages — can depend on the contract layer without silently pulling runtime, and that the contract layer cannot accrete behavior.
- API4. A package's public surface is its `exports` map: the root `.` is required, `./package.json` is required so tooling can read the manifest under exports encapsulation, and every extra key is a first-class documented subpath rather than a `./src/*` or `./dist/*` escape hatch. `scripts/published-exports.mjs` fails on a missing `.` or `./package.json`, an unmarked extra key, or a stale allowlist entry, and the `no-pen-deep-imports` lint bans `/src/` and `/dist/` specifiers monorepo-wide including apps and docs, so the boundary is dogfooded rather than merely published. Glob extra keys are the same class and are closed by enumerating the subpaths that have live published-path importers, so a new file under a previously globbed directory is not public on the next build; documentation coverage (`scripts/api-docs-coverage.mjs`) expands any remaining glob key to a name inventory and feeds those names into the undocumented-symbol ratchet, which may only decrease, and a declared glob that lists zero files or a listed member whose `.d.ts` cannot be read fails closed. Symbols exported from a package index but not intended for hosts carry `/** @internal */` and are stripped from the published `.d.ts`; the playground and docs must not import internals, so a needed internal either becomes public deliberately or the feature moves inside the package, and every package commits an API report generated in CI where a report change requires the `api-change` label and a changeset — the mechanical gate for whether the public surface just widened. The report is a name inventory and will record a phantom identifier as readily as a real one: a published `.d.ts` `export { Name }` with no `type` keyword, no `from` module, and no local or imported binding is a packaging defect, because that is how the declaration bundler flattens a type-only value-style re-export into a name that appears in the file and in the report while a host still cannot resolve it. Workspace `tsc` uses `skipLibCheck` and will not see it. `scripts/api-reports.mjs` rejects that shape. Type-only public names are authored with `export type` or `export { type Name }` so the emit keeps a type binding.
- API5. `BlockHandle` carries only the universal surface — `id`, `type`, `props`, `content`, children traversal, `textContent()`, `length()`, and prop get and set through ops — and per-block-type capability surfaces live behind a typed accessor, `block.as("table")`, which returns `null` when the block's schema does not declare that capability. Capability keys are declared by schemas and typed through a capability registry, so call sites read as intent (`block.as("table")?.cellAt(row, column)`) instead of every handle pretending to be every block type, and using an unchecked capability handle is a type error. That registry is the single vocabulary for what a block can do across selection, commands, and handles, absorbing the older ad-hoc capability checks.
- API6. Behavior lives in `@input/pen-dom`, or in `@input/pen-core` when it is DOM-free; `@input/pen-react` and `@input/pen-vue` contain only framework bindings — components, hooks and composables, context plumbing. A module that exists in both renderer packages, or that imports neither its framework nor a framework type, is in the wrong place: the `no-framework-free-modules-in-renderers` lint requires such a file to justify itself in a disable comment with a reason. Parallel implementations of the same logic are how React and Vue drift apart, and a byte-identical duplicate pair is the lucky case rather than the safe one.
- API7. Versioning is a single coordinated train across every published package, produced by one changesets `fixed` group listing every published package and enforced by a version-sync check: unpublished placeholders stay at `0.0.1`, the first published train is `0.1.0`, and the train stays `0.x`, where a breaking change takes the minor position, so `0.2 → 0.3` is a legitimate breaking release and no deprecation window is required. On `0.x` a changeset `major` is rejected (`changeset-check`); breaking is `minor` and additive is `patch`, because `major` would jump the train to `1.0.0`. Every changeset body ends with `Breaking: yes — <what a host must change>` or `Breaking: no`, and `changeset-check` fails on a missing line, on `Breaking: yes` with a `patch` bump, and on `Breaking: no` with a `minor` bump, so grading is a recorded decision the gate holds consistent. A breaking change that shipped as a patch is recorded as an erratum under its version heading in the affected `CHANGELOG.md`. Releases run through changesets with per-package `CHANGELOG.md` generation and a git tag per train; publishing runs `publint` and `are-the-types-wrong` with `--profile node16`, because a node10 resolver cannot read an exports map and every package declares an `engines.node` floor above it, so package roots resolve under node10 but subpaths deliberately do not, and publishing is `pnpm release` from a maintainer terminal after the GitHub release workflow opens and merges the Version Packages pull request — that workflow does not publish. Published manifests are uniform, checked by `scripts/sync-package-metadata.mjs` rather than by review: one workspace pin style (`workspace:^` throughout, because the exact-version rewrite at pack time installs duplicate Pen modules on any version skew — the same failure mode API2 prevents for Yjs, self-inflicted), one ESM artifact extension, `sideEffects: false` on every published package, and every `exports` map includes `./package.json`. Bundle budgets are regression gates rather than absolute targets — `size-limit` baselines are recorded per package in `.size-limit.baseline.json`, a regression above 10% fails the `size-limit` repo gate (`scripts/gates.json`, `.github/workflows/static-analysis.yml`) on every pull request, a code-split package is weighed as its whole shipped ESM closure (`dist/*.mjs`), and intended growth is re-recorded in the same change with a note that cites the rule that moved it and accounts for the bytes — `scripts/size-limit.mjs` fails a re-record dated 2026-10-02 or later whose `Re-recorded baseline <date> (<rule IDs>)` parenthetical names no shipped rule ID; there is no override label, because a label leaves no record in the file — and CI runs a matrix across the endpoints of the declared `engines` range plus at least one non-Linux runner, because a declared support range verified on one version is a guess.
- API8. Pen is licensed under the MIT License (`LICENSE.md`), copyright Input B.V., may be described as open source, and its positioning language matches the license exactly: no production-use restriction, no license-enforcement clause, and no enforcement code in the source. Publish-access claims and manifests agree — `.changeset/config.json`, `scripts/sync-package-metadata.mjs`, and every published manifest set `publishConfig.access: "public"`, while packages that must stay internal (the docs app, the playground, the examples, the ESLint plugin, and the conformance harness) keep `private: true`, are skipped by the sync script, and are listed in `.changeset/config.json` `ignore` (`changeset-check` fails if that list drifts from the private workspace set), so they are never published. Published manifests name the repository that publishes them, with `homepage`, `bugs`, and `repository.url` matching the remote and `CODEOWNERS`; this is a release requirement rather than cosmetics, because the registry rejects a provenance publish whose `repository.url` names a different repository. Inbound and outbound licenses are asymmetric on purpose and the asymmetry is stated where contributors read it (`CONTRIBUTING.md`): outbound is MIT, inbound is the `CLA.md` copyright and patent grant to Input B.V., and concentrating copyright in one holder is what makes a relicense possible without contacting every past contributor — replacing the CLA with a DCO would forfeit that, so amending this record is the first step if it is ever dropped.
- API9. Table grid execution stays with the table block rather than becoming a general core concern. It still lives under `packages/core/src/editor` (`tableGridExecutor.ts`, `tableGridCellHelpers.ts`), and extracting it is recorded as deferred to v2.1 rather than in progress.
- API10. A symbol in a published package's public surface is in exactly one of three states, and the state is visible from the type: implemented, meaning it does what its name and signature say; host-implemented, meaning an interface member Pen never calls, documented as such in its TSDoc; or absent. There is no fourth state where the type promises and the runtime shrugs, and the rule covers every public shape — props accepted by exported components, option-object fields, event names in an event map, and members of a discriminated union a consumer can emit — because the usual review reflex, whether a function works, never catches those. Enforcement is a per-release inventory rather than a lint, since no lint can decide whether a value is used meaningfully: every entry in a package's API report resolves either to a test that exercises it or to a TSDoc `@remarks` line stating that Pen never calls it, and the release workflow fails on an unresolved entry, so an unwired surface fails the same review that already catches a widened one. Discriminated unions get the mechanical version — a consumer handles every member or the build fails — and where exhaustive handling is genuinely not wanted, the unhandled members leave the inbound union type. Absent API costs an adopter one search; inert API costs them a debugging session plus their confidence in every other type in the package, which for an SDK whose primary documentation is its type definitions makes a lying type a documentation defect with a compiler's authority behind it.

## SF — package surface consolidation

- SF1. The AI family is one package, `@input/pen-ai`, with subpath entries per feature: `.` for core AI plus the egress seam, then `./suggestions`, `./autocomplete`, `./skills`, `./tools`, and `./stream`. Imports between those features are relative, which makes the egress choke point single-definition by construction rather than by discipline.
- SF2. The import and export family is one package, `@input/pen-interop`, with per-format subpaths (`./html`, `./markdown`, `./json`, `./xml`), each exporting that format's importer and exporter. `packages/shared/markdown` stays a shared package for as long as it has a consumer outside those formats; it folds into `@input/pen-interop` only when the merged formats are its sole consumers.
- SF3. One later merge is recorded as an amendment to this rule: the two transports became `@input/pen-transport` with `./direct` and `./sse` subpaths, the SF1/SF2 shape applied to a two-variant seam whose members shared one dependency footprint and one release cadence. Nothing else merges: multiplayer, search, autoformat, shortcuts, undo, snapshots, tools, ingest, markdown, schema, the starter, and the tooling packages keep their boundaries, and that list is closed, so extending it amends this rule rather than being decided in passing. The governing test is that a package exists when it has an independent consumer, an independent dependency footprint, or an independent release cadence — not because a feature was developed in a separate folder.
- SF4. A merged package ships the workspace manifest standard: dual ESM and CJS, an `exports` map covering every subpath including `./package.json` (required on every published package, not only merged ones), a `files` allowlist, `sideEffects: false`, and peer ranges taken from the strictest of the merged manifests. `scripts/sync-package-metadata.mjs` runs as part of the merge, and the Verdaccio full-closure install is the verification that matters — publish the closure to a local registry, `pnpm add` the top-level packages in a clean temporary project, build, and run the mount-and-edit smoke test — because it is the only check that exercises `exports` maps, `files`, and peer ranges the way a host does.
- SF5. Retired. The satellite specifiers it governed (`@input/pen-ai-suggestions`, `@input/pen-delta-stream`, `@input/pen-export-json`, and the rest) were folded into `@input/pen-ai/*` and `@input/pen-interop/*` before anything was published, so no consumer ever imported them and there is no host-side rewrite left to sequence. The workspace rewrite is complete. What keeps the retired names from returning is API4 and the published-export allowlist, which enumerate the export keys a package may ship, not a prose mapping table.
- SF6. `api-report.md` files, the documentation-coverage ratchet, and the `size-limit` baselines are re-recorded in the same change that moves the surface they describe, never spread across follow-ups, because per-lane ratchet edits are how baselines rot. Retired package names are deleted from the workspace rather than kept as aliases; because they were never published, they are not `npm deprecate`d.
- SF7. `@input/pen` is the brand name and belongs to the starter package — the default preset plus core's editor constructors wrapped to default an omitted `preset` to `defaultPreset()`, the one name a quickstart installs. Every other published name is `@input/pen-<name>` with exactly one word after the prefix, and the word names the product area the package owns: `pen-core`, `pen-dom`, `pen-react`, `pen-vue`, `pen-yjs`, `pen-ai`, `pen-interop`, `pen-schema`, `pen-tools`, `pen-ingest`, `pen-markdown`, `pen-transport`, `pen-autoformat`, `pen-snapshots`, `pen-undo`, `pen-search`, `pen-shortcuts`, `pen-multiplayer`, `pen-types`, `pen-test`, `pen-bench`, `pen-assets`. A seam with several implementations does not put the variant in the name — it becomes one package with a subpath per variant, the SF1/SF2 shape, which is how `pen-transport` ships `./direct` and `./sse` and how a second schema set or asset provider would arrive as a subpath rather than a sibling name. Exceptions to the one-word form are recorded in this rule when they are made; there are none. The directory group is repo navigation and never appears in the published name — `packages/crdt/yjs` ships `pen-yjs`, `packages/rendering/react` ships `pen-react` — so a package that moves between groups keeps its name. A name that claims a concept the package does not own is a defect and gets renamed, which is why `pen-document-ops` (colliding with the `DocumentOp` union it merely consumes) became `pen-tools` and `pen-history` (reading as undo everywhere else in the ecosystem) became `pen-snapshots`; two names that share a word while owning different roles survive, which is how `pen-tools` defines the document tools and `@input/pen-ai/tools` grants them to a model. Companion packages are published because published packages depend on them rather than because a host should install one — `pen-types`, `pen-ingest`, and `pen-markdown` — and they are named for what they contain rather than marked internal, because a name is not the place to carry install advice: DOC4 puts the redirect in the first sentence of the README and `scripts/readme-sections.mjs` holds the list, and DOC1's doc gate keeps every published name, companions included, visible in the root README package table. Until the first train a name is free to change; after `0.1.0` a rename is a breaking change under API7, and SF3's closed list is the record of which names exist.

## CS — internal structure

- CS1. Core's internal seams are typed rather than `any` bags: the apply-pipeline and editor-implementation runtime contexts are explicit internal context interfaces, the thin private-forwarding wrappers on `ApplyPipeline` (`_validateOp` delegating to `validateOp(this, op)` and its kin) do not exist, and the CRDT text shape has one definition (`CRDTTextLike` in `crdtShapes.ts`) rather than a local copy per module. Typing these seams changes no pipeline phase, no hook ordering, and no commit semantics; it is types and indirection only.
- CS2. `editor/selection.ts` is split along its existing seams — endpoint validation and clamps including the N2 mixed-boundary rules, commit-time repair-then-resolve, and the authority record and event surface — as separate modules with the same exports and no new concepts. The `authorityCompare` traces and the selection conformance suites are the behavioral pin for that split.
- CS3. Oversized command modules split by domain, not by line count: `commands/caret.ts` by motion versus vertical measurement, `commands/text.ts` by enter and split versus delete versus payload factories, and `commands/helpers.ts` down to the factories its consumers actually share. Catalog registration and command names are frozen across such a split.
- CS4. Grep-visible names that contradict the architecture are renamed in place rather than left as a permanent reader tax: the mapping-era `changes/mapping.ts` folds into `changes/summaryBuilder.ts`, because change summaries describe what a commit touched and do not map positions across commits.
- CS5. Selection input and output has one orchestration: `decideDomSelectionRead` decides, the projection controller writes, and the EditContext, contenteditable, and expanded backends keep only their genuinely different primitives (EditContext `updateSelection` versus a native range write). The consolidation moves code to where its spec says it lives and must not redecide anything the reader decides today — in particular the two contenteditable restore predicates (a full-block echo against a collapsed caret, and collapsed DOM against a projected stamp) fold onto the projector rather than into the read decision, because folding them into the read would redecide open-window accepts. **This rule is not a finished contract.** Selection bridging inside `@input/pen-dom` is the one part of the surface still unsettled, `spec/packages/rendering/dom.md` marks it as such, and the current bridge should be treated as the subject of an in-progress redesign rather than as an interface to build on.
- CS6. There is one frame authority: the session reconciler's `requestAnimationFrame` coalesce runs on `DomScheduler` rather than on a private rAF, so a write-phase reconcile happens before the post-flush selection projection, a history flush shares the scheduler frame and projects after the reconcile, and a pending reconcile that arrives without a scheduler still projects once one flushes. Pinned by `packages/rendering/dom/src/__tests__/scheduler.cs6.test.ts`.
- CS7. `geometry/geometryReader.ts` splits into caret and rect measurement, hit-testing (`pointAt`), and bidi-run packing, leaving the G1–G5 geometry rules unchanged; the geometry conformance scenarios are the behavioral pin.
- CS8. The React binding sheds what belongs below it and its manifest matches its design: framework-free gesture handling and inline-atom interaction live in `@input/pen-dom` behind framework-free interfaces with the React hooks as thin subscriptions, AI preview logic lives in `@input/pen-ai` or behind the `./ai` subpath, and the optional feature packages (`ai`, `history`, `multiplayer`, `search`, `interop`) are `peerDependencies` matching the subpath opt-in rather than hard `dependencies`. A package cannot be both a dependency and an optional peer; the React `test` script relies on the Turbo dependency graph rather than hand-rolled sibling builds, and both install profiles — optional peers satisfied and optional peers absent — must pass.
- CS9. `@input/pen-dom`'s export surface is curated and shrinking rather than accreting: single-consumer utility subpaths fold into the barrel, the consumer census of which of React, Vue, conformance, and the playground imports which subpath sets the target rather than taste, and `scripts/published-exports-allowlist.json` is re-recorded to agree with the export map in the same change that changes it.
- CS10. jsdom does not pretend to be a selection engine: pen-dom tests that exercise `window.getSelection` semantics jsdom does not implement move their engine-fidelity assertions into conformance scenarios and keep only their pure-logic assertions as unit tests. Shared fixture corpora belong in `@input/pen-test` rather than being near-duplicated per interop format, and duplicated test trios collapse to one file. Pinned by `packages/tooling/conformance/suites/selection/cs10-mapping.spec.ts`.

## Retired

`SF5` is retired: it sequenced a specifier rewrite that finished before first publish, and its table lived in the host migration guide, which is deleted for the same reason — nothing was ever published under the retired names. API1–API10, SF1–SF4, SF6, SF7, and CS1–CS10 are live.

## Dropped

No `CS` rule was dropped: all ten describe the intended structure of the shipped system rather than a migration step, and CS6 and CS10 are claimed by the tests named in their rule text. What was dropped is the migration scaffolding those rules were written inside — step sequencing and per-slice ordering, seed-time line counts and export-key counts used as thresholds, "regenerate the population" instructions, exit-gate narration, and the ratchet-commit discipline, which survives in CS9 and SF6 only as the durable requirement that a ratchet is re-recorded in the same change that moves the surface it describes.

The same trimming applies to `API` and `SF`: step assignments, audit finding numbers, and the pre-migration evidence paragraphs are gone. Where a counterexample was the only thing that made a rule legible, its shape is kept and its file-and-line citation is not. Two API7 clauses are dropped as project process rather than product rules: the release-permission clause, and the record of how authored changeset bumps differ from the computed result.
