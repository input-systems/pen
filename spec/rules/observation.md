# Observation And Intent

A `ChangeSummary` answers exactly one question: what did this commit touch. It never answers where a position went — that is anchors, `spec/rules/anchors.md` — and it never claims to know why something changed unless the origin says so. `OB` governs the summary contract and its builder; `INT` governs `origin.intent`. Contracts live in `@input/pen-types` (`types/changes.ts`, `types/ops.ts`) and the builder, helper, and dispatch stamping in `@input/pen-core` (`core/src/changes/`, the command registry).

## OB — Change Summaries

- OB1. Summaries carry effect plus the two content-move recipes. `block-converted` does not exist: a conversion appears as `block-props-changed` with `"type"` among `keys`. `block-split` and `blocks-merged` stay because anchor repair needs their geometry — source, destination, and cut or join offset — stamped by the local executor inside the commit's transaction and copied onto the summary, not reconstructed from deltas and not a command name. Remote commits carry no such stamp, and nothing reconstructs intent names from deltas. When a recipe is present the builder suppresses the generic inserted/removed pair for the same blocks, because emitting both would double-apply the move.
- OB2. One builder, one code path: the summary builder consumes transaction deltas and serves local, remote, undo/redo, and stream commits through the same code. It constructs no position-mapping structures and emits nothing beyond the summary contract.
- OB3. The splice helper is a function, not an algebra. `mapOffsetThroughSplices(splices, offset, assoc)` is a pure per-block clamp for derived-tier providers shifting results within one summary. There is no `compose`, no multi-summary form, no map modes, and no cross-commit law; code that needs a position to survive more than one commit uses an anchor (I13).
- OB4. Summaries stay content-free: lengths, offsets, IDs, and keys only, never copied text. The rule stands on its own and does not decay with the retention pressure that first motivated it.
- OB5. Summaries are not retained. A `CommitEvent` carries its own summary and a flush carries batched events; there is no summary ring buffer and no cross-commit summary window. Late consumers such as an AI response arriving several commits after its request use anchors, which do not expire.
- OB6. `CommitEvent` is otherwise unchanged: `commitId`, `origin`, `selectionBefore` / `selectionAfter`, `source`, and `diagnostics` keep their contract, and only the `summary` field's type narrows. Commit numbering starts at 1 for the first observable commit — constructing a document is not a change to one, so the pending-migration pass, the profile write, and the initial paragraph consume no id, and a freshly created editor is handed over in the same state as a loaded one: no last change summary, next commit 1.

`StructuralChange` is closed at nine variants: `block-inserted`, `block-removed`, `block-moved`, `block-props-changed`, `block-split`, `blocks-merged`, `table-changed`, `apps-changed`, and `metadata-changed`. An exhaustive switch over its `type` is the compile-time gate on that closure. A removed block takes its `children`-array subtree out of the document with it, and the summary reports `block-removed` for each such descendant the same commit did not re-home elsewhere (with the parent and index it held), so a per-block index drops it without walking the document; the cost is bounded by the removed subtree (SCALE2). A descendant's stored map can outlive the removal, so a consumer treats a removed id as gone rather than re-reading it: scoped decoration sources are not asked to re-read removed blocks, and the AI suggestion list, review decorations, and search matches drop them.

## INT — Intent On The Origin

- INT1. Dispatch stamps intent: when a command handler's result produces an apply, the command registry sets `origin.intent` to the command's frozen name before the pipeline runs. Handlers and hosts may not overwrite a stamped intent, and a caller-supplied `intent` survives only when no command is on the dispatch stack, which is how a programmatic apply names itself.
- INT2. Nothing synthesizes intent. Remote commits, undo/redo, and stream flushes carry no `intent` unless the originating local commit's origin already had one and it was preserved verbatim. No inference, no defaults, no guessing that something was probably a split.
- INT3. Consumers that need to know why read `origin.intent` on local commits and treat remote commits as effect-only, which is the only honest option a remote commit ever allowed. Consumers that need effect read `block-props-changed` with `"type"` in `keys`. Split and merge readers outside the repair-geometry allowlist do the same; that allowlist — the producer plus the repair, non-text selection, shadow-index, and dirty-block extractors — reads recipe geometry, never intent.

Intent names the user's gesture, not the structural outcome. A merge reached by pressing Backspace at a block boundary carries `intent: "pen.deleteBackward"`, and there is no merge command to name; the structural outcome travels on the summary recipe instead. A recipe must never stamp a name that nothing dispatched, because that would turn `intent` into a synthesized label and break INT2.
