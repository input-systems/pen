# Content Interoperability And Assets

Interoperability is where an editor meets the rest of a user's software, and it is the part users judge instantly. This document owns content crossing Pen's edges: the clipboard payload and what happens when it meets a different Pen, fidelity when pasting from real applications, what each exporter preserves and loses, the lifecycle of binary attachments, and the bounds every ingestion path shares. It governs transfer and clipboard code in `packages/rendering/dom`, the import and export paths in `packages/extensions/interop`, `packages/shared/ingest`, the default schema's serializers, and the asset contracts in `packages/types`. Sanitization, URL policy, escaping, and prototype-pollution defenses are owned by the SEC rules and are not restated here; this document is the fidelity half.

## IOP — Content interoperability and assets

- IOP1. The Pen clipboard payload is a self-describing envelope carrying `PEN_CLIPBOARD_PAYLOAD_VERSION` and the sorted set of block types it contains, which is enough schema identity to decide paste behavior by comparison rather than by luck and requires no registry versioning from hosts. A matching version with all types known takes the direct block-paste fidelity path; a matching version with some types unknown falls those blocks back to the HTML flavor with an `import-dropped` diagnostic naming each type; an older payload is migrated for its version and then treated as matching; a payload with no version field is treated as version 0 and migrated; and a payload newer than the reader is read through the HTML flavor only, with a diagnostic, because the JSON flavor is never partially read. Falling back to `text/html` rather than dropping is what makes cross-version paste acceptable — the user gets formatted text instead of nothing and the diagnostic tells the host's telemetry what was lost — which is why the `text/html` flavor stays a first-class output and not a legacy artifact.
- IOP2. A committed corpus of real clipboard captures — Microsoft Word desktop and web, Google Docs, Apple Notes, Notion, a plain web article, and a Pen-to-Pen copy — stores the actual `text/html` and `text/plain` pair each source produces, captured once by hand and never hand-edited afterwards. Each capture has an expectation file asserting structure rather than bytes (block sequence and types, heading levels, list nesting depth, marks present per range, table dimensions, image count), and intentional losses are recorded in the expectation so the corpus documents the paste contract instead of merely guarding it — a loss that is not in the expectation is a regression. Pen does not sniff the source: it never branches on Word's `mso` classes or Google's GUID comments, so a defect a capture reveals is fixed in the generic conversion rules, and the corpus runs against real browser clipboard events where possible because clipboard behavior is browser behavior.
- IOP3. One published fidelity table per format (HTML, Markdown, JSON, XML), generated from the schema's serializers rather than written by hand, classifies every default block and mark as lossless, lossy with what is lost named, or Pen-specific (round-trips through Pen only). JSON and XML are the interchange formats and are contractually lossless for schema-known content, asserted by a round-trip property test over generated documents that compares `apps`, `metadata`, and unknown props as well as blocks; HTML and Markdown get round-trip property tests at the fidelity their table claims, so a lossless-classified block must survive export and re-import and a lossy one must lose exactly what its row describes, and a serializer whose behavior does not match its row fails. HTML export calls the block schema's `serialize.toHTML` when present, including for `image` (SEC1 still rewrites `<img src>`) and list items (run wrapping keeps the schema `<li>` attributes). Markdown is named for what it is — GitHub-flavored Markdown for blocks with a standard representation plus Pen extensions for blocks without one — and fallback serialization stays because text in a paragraph beats an exception, but it reports, emitting an `export-fallback` diagnostic naming the block type so a host shipping a custom block learns it has no serializer before its users do.
- IOP4. Declared asset options are passed rather than decorative: the provider's `maxSize` is enforced before the upload call and `onProgress` is invoked during it. Upload failure is a first-class outcome — an `asset-upload-failed` diagnostic per file carrying the file name, size, and the provider's error, plus a partial insert when some files succeeded — because silence is the one unacceptable behavior when the user watched an image not appear. HTML image ingestion has a stated policy with a default: `"keep"` preserves a remote `<img src>` as a remote reference, which is today's behavior made explicit, while `"ingest"` routes http(s) and admissible `data:` URLs through the editor's `AssetProvider`, and a `data:` URL above the shared size cap is either promoted through a configured provider or dropped with a diagnostic, since an unbounded `data:` URL landing in a `gc: false` collaborative document is a durability failure with a paste-shaped cause. Asset deletion is host-owned and documented as such, because Pen cannot know whether an asset referenced by a deleted block is also referenced by another document, a version snapshot, or a collaborator's pending undo: `AssetProvider.delete` stays in the interface as a host-called method that Pen never calls, and what Pen provides instead is the observable signal — a document's referenced assets are enumerable — so a host can build reference counting.
- IOP5. One set of shared caps governs every ingestion path — the JSON clipboard flavor, HTML paste, HTML import, Markdown import, and XML import — with identical numbers rather than per-path values, because one document arriving by two routes must not meet two limits: `INGEST_MAX_NESTING_DEPTH` 32 (which list `indent` shares), `INGEST_MAX_NODE_COUNT` 10,000, `INGEST_MAX_TEXT_SIZE` 1,048,576 UTF-16 code units, and `INGEST_MAX_IMAGE_COUNT` 256, plus caps on attribute and prop string length and on `data:` URL length. Exceeding a cap truncates at a block boundary and reports: the content that fit is inserted, and an `import-truncated` diagnostic names the bound, its limit, and the measured value, so a pathological paste degrades to a large-but-finite document rather than an unresponsive tab. `INGEST_TIME_BUDGET_MS` (1000) is a recorded bound and not a pass/fail gate, because a wall-clock on a shared CI machine measures the runner; the suite asserts the countable invariant underneath instead — a source longer than `INGEST_MAX_TEXT_SIZE` is sliced or refused before parse, so admitted work is proportional to the cap and not to the input — and all of these numbers are documented as part of the paste contract rather than buried as security constants, because a host importing a legitimately huge document needs to know them and how to raise them.
- IOP6. Every entry point that can discard content returns or emits the same violation record: the parse helpers return violations alongside blocks and the paste path emits diagnostics, so there is no supported way to lose content without a signal. One violation vocabulary spans every path — the `import-dropped` code with a reason (`unknown-block-type`, `profile-disallowed`, `depth-exceeded`, `count-exceeded`, `text-size-exceeded`, `image-count-exceeded`, `invalid-props`, `forbidden-key`) and a count per reason, escalating to `import-truncated` when the reason is a declared bound — rather than two codes for one event, and the published diagnostic table carries the result. Diagnostics are aggregated per operation and not per block: a paste that drops 400 blocks emits one record per reason with a count, because per-block emission is how hosts learn to ignore the channel.
- IOP7. Clipboard slice and paste keep inline atoms. `sliceDeltas` treats an embed insert as length 1 in the same offset space as string inserts and retains the embed when any of that unit falls inside `[from, to)`. Single-block copy always slices `inlineDeltas()`, not `textDeltas()`, so a full-block copy still carries embed records in `penBlock.deltas`. Paste rebuilds those records into `splice-text` inserts `{ nodeType, props }` on both the inline-fragment path and the new-block path. `block.textContent()` is unchanged: it stays stored string text without embed contribution. Caret offsets and `block.length()` include each atom as one unit; lookbehind that mixes `textContent()` with those offsets is a domain error (N6).
- IOP8. Interchange flavors ask the inline-atom schema for text. `InlineSchema.serialize.toText(props)` is the optional plain-text hook for `kind: "node"` atoms; `toMarkdown` and `toHTML` keep the existing mark shape `(text, props)` and are called with empty `text` because an atom has no inner string. Clipboard `text/plain` uses `toText`, then `toMarkdown`; markdown uses `toMarkdown`, then `toText`; HTML uses `toHTML` when present, otherwise the plain fallback escaped per SEC5. An atom whose serialize bag is empty is skipped in every interchange flavor — that is the documented default, not a drop diagnostic. Hosts register the hooks on the inline schema they pass to `schema.extend` / the registry `inlines` list; `resolveInline` is the lookup.
- IOP9. Block paste — parsed HTML or Markdown and full blocks from the Pen clipboard payload — lands at the caret, not after the caret's block. After the selection is deleted, the first pasted block joins the text before the caret when both are inline-content blocks, the last pasted block joins the text after it the same way, and any blocks in between split the caret line, which keeps its block id and type. An empty caret line is replaced by the pasted blocks, and a caret in a block without inline content inserts after that block. The caret ends after the last pasted content. Hosts customize what a paste parses into through the `clipboardFacet` importers, never where it lands, so one placement rule serves every host.

## Retired

No `IOP` member is retired. IOP1–IOP9 are all live. One surface element was retired rather than a rule: the separate import-drop diagnostic code was reconciled into the single `import-dropped` / `import-truncated` vocabulary under IOP6.
