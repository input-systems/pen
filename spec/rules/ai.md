# AI Boundary

Pen ships no vendor SDK and makes no network call of its own: model access goes through a `ModelAdapter` the host injects, and transports go through `PenTransport`. This document owns the contract across that boundary — what document content leaves the browser and under whose control, what a model-driven tool may do to a document, how an AI action appears to undo, how the stream protocol evolves, and how a host tests any of it — and it owns the uniqueness of the durable edit channel (UC) and the host-facing presentation of proposed edits (RS). It governs `packages/extensions/ai` and its subpaths, `packages/extensions/tools`, the stream and tool contracts in `packages/types`, `packages/transport`, and the model doubles in `packages/tooling/test`. Semantics of the surviving channel itself (`EC1`–`EC21`: addressing, refusals, streaming preview of a tool call, undo grouping of a run, host reuse of the compiler) live with the package they govern, in `spec/packages/extensions/ai.md`; where a UC rule and an EC rule appear to conflict, the EC rule wins, except that the coexistence flag those EC rules were written beside is gone — there is one channel, and it is not optional.

## AIB — AI boundary

- AIB1. Every request Pen assembles passes through one egress facet — `pen.aiEgress`, resolved through `aiEgressFacet` in `@input/pen-core` and re-exported by the AI package — before it reaches a `ModelAdapter`, carrying a structured `AIRequestContext` of feature, messages, per-block document excerpts tagged `selection`, `target`, `context`, or `tool-result`, and tool schemas, rather than a pre-rendered prompt string, because a host redacting content needs to know which text is document content and which block it came from. Returning `null` cancels the request with an `ai-request-refused` diagnostic and no model call: a refusal is a normal outcome that reports the feature as unavailable for that invocation and leaves the editor running, not an error. Every AI feature routes through the facet, including autocomplete and proactive suggestions, since the host that needs redaction needs it most on the feature that fires every few keystrokes, and the filter is synchronous and cheap — asynchronous review belongs in the host's `ModelAdapter`, which is already where network work lives.
- AIB2. One published table, generated from the exported constants rather than written by hand, states for every AI feature what document content it includes, the maximum characters it will send, and what triggers it, because a host's privacy review is a real document that someone signs and today it would need a code reading. Every bound is a named exported constant with a default that the AI extension's config can override, and nothing sends unbounded document text, including the agentic working set; tool results that re-enter a prompt are excerpts like any other content, under the same table, the same caps, and the same egress facet, because that is the path that grows silently as each step's output becomes the next step's input. `PenStreamRequest.context` carries no `editor` field — a field typed `unknown` on a serialized request is an invitation to send the editor instance to a server, and `unknown` means the compiler cannot decline — but the explicit serializable subset instead, and the docs state the thing hosts most need and cannot infer: Pen sends nothing anywhere on its own, and every byte in the table travels only through the adapter the host wrote to the endpoint the host chose.
- AIB3. Tool availability is a host-controlled allowlist resolved as a facet, defaulting to the tools the enabled extensions register, so a host shipping AI reading but not AI writing expresses that in one line rather than by not installing a package other features need. Destructiveness is classified per call: a tool descriptor declares `destructive` as a fixed flag or as a resolver that reads the call's complete input and whether its writes stage as suggestions, and a call classified destructive passes through a confirmation seam — a host-provided resolver that may allow, refuse, or defer. Whether writes stage follows the mutation mode the running generation bound; each generation's binding is its own entry, so generations that overlap (one cancelled after the next has bound) unbind only themselves and the most recent live binding decides — an earlier generation's unbind never turns a later one's staged writes durable (pinned by `aib3.mutationModeBinding.test.ts`). The tool-call write guard follows the same rule: each open call holds its own layer and closing removes only that layer, so an out-of-order unwind never restores over another call's guard (pinned by `aib3.writeGuard.test.ts`). A write is attributed to the call that issued it, not to whichever call opened last: each call's handler runs with its own context, whose editor, streaming target, and stream writers carry the call's identity, so every write path refuses a read-only call's write and books a mutating call's write to that call's group and budget while calls overlap; a write made through the shared editor that no call can be named for belongs to the only open call, and with several open is refused while any of them is read-only (pinned by `aib3.callAttribution.test.ts`). `edit_document` staged as suggestions is never destructive, because review is the confirmation and nothing lands until accept; applied directly it is destructive only when it removes or replaces existing content — `delete_blocks` over a block that is not empty, `replace_blocks` over a block that holds content, `replace_block_text` over non-empty text, or `set_block_props` that changes the content kind of a non-empty block, for example paragraph to divider — while inserts, moves, formatting, and deleting an empty block are not. `delete_block` and `write_document` are always destructive; they serve the external tool surface (UC7). A resolver that throws is read as destructive. Absent a confirmation resolver, `aiExtension({ unconfirmedDestructive })` decides: the default `"allow"` runs the call and emits `ai-tool-unconfirmed`, and `"refuse"` blocks it with the document unchanged, which is the setting for a production host that exposes the external tools; the external tool surfaces — `directTransport`, `createSSEHandler`, and `processStream` — run their turns under the editor's configured `confirm` / `unconfirmedDestructive` (published by `aiExtension` on `aiToolConfirmPolicyFacet`) and take explicit `confirm` / `unconfirmedDestructive` options that win over it, so a host's refuse setting reaches every surface that runs a model's tool calls (pinned by the `aib3.authority` tests of both transports and `processStream.aib3.authority.test.ts`); a deferral is an answer that blocks the call and must not also take the allow-with-diagnostic path. Budgets are declared, defaulted as named constants, and enforced by the loop — model passes per run, tool calls per turn, document ops per call and per turn, and a wall-clock deadline — and exceeding any budget ends the run with a reported reason rather than an exception, leaving the partial result in whatever review or suggestion surface the run was writing to; Pen does not meter tokens or cost, because the adapter owns the model call and an invented estimate is a number hosts would trust. Every mutation a tool makes stays an `editor.apply` through the standard pipeline with a tool-attributed origin, so validation, normalization, and suggest mode still apply — tool authority is about whether, never about bypassing — and because the tool-execution sink is reachable without a grant from in-process host callers, adding a caller of the tool executor or the validated-op applier is a security change reviewed as one.
- AIB4. An AI action — one generation, one accepted suggestion, one agentic run — is one undo step for the user, where the unit is the action the user asked for and not the number of ops it took. The group identifier is created once where the action starts and threaded through every write the action performs, including tool applies, streamed block ops, and host-driven streams, so an AI write path that cannot name its group is a bug in that path; grouping is keyed rather than timed: every write that carries the group identifier joins that action's single undo step while the step is on the stack, and the step moves to the top when it receives a write, so a user's typing or a collaborator's edit between two writes of the action neither closes the step nor joins it, and the user's own ungrouped typing groups by the capture window only with the step directly beneath it, so it never merges across another action's step. The capture key travels with each apply rather than living in ambient state, so an apply issued from inside another apply — queued by the pipeline until the running one finishes, as an apply-boundary listener's is — captures under its own group or origin key and never joins the outer apply's step (pinned by `aib4.interleaving.undo.test.ts`). `stopCapturing()` never closes an explicit group; undo and redo close every open group, so the next write of a still-running action starts a new step. A group identifier names one action, and reusing it while its step is on the stack joins that step — except when a later step on the stack deleted text the group inserted: the step cannot move past that deletion without undoing it out of order and bringing the deleted text back, so the group's open step closes and the write starts the group's next step (pinned by `undo.keyedCapture.test.ts`). A run the user cancels mid-flight is still one undo step covering what landed before the cancel, since partial results the user can see must be reversible in one action, and the documented limit is that undo is per-client: undoing an AI action reverts this client's ops and cannot revert a collaborator's interleaved edits, and `packages/extensions/multiplayer/README.md` works that case through with a collaborator's edit inside the AI change (pinned by `aib4.collaboratorUndo.test.ts`). Pinned at the stream level by `stream/__tests__/aib4.undoGrouping.test.ts` and at the controller level by `aib4.controllerCancel.test.ts`, which cancels a session mid-stream and interleaves user typing in another block.
- AIB5. The stream protocol carries a version (`PEN_STREAM_PROTOCOL_VERSION`), the consumer checks it, and a mismatch is a diagnostic and a refused stream rather than a partially applied document. Part handling is exhaustive: the part `switch` ends in a `never` check so a member added to the union without a handler fails the build, no inbound member is left silently inert, and unknown parts from a newer server are dropped with a `stream-part-unknown` diagnostic once per part type per stream, because silently ignoring a part is how a host spends an afternoon debugging a document that never changes. Known parts are validated before they reach the document — required fields present and correctly typed, ids non-empty, ops built from validated fields — and the consumer degrades rather than asserts, treating a missing streaming target as a diagnostic and a refused stream instead of a non-null assertion; the wire format is documented as a wire format (parts, fields, ordering rules, and version policy) because a host writing a server implements it from documentation.
- AIB6. `@input/pen-test` exports a scripted mock `ModelAdapter` and a stream fixture builder driven by a declared sequence of parts, with controls for delay, abort mid-stream, error parts, and malformed parts, so a host can test its AI integration without a model and without a network. The mock is the same one Pen's own suites use, because a fixture only the library's tests exercise drifts from the shapes hosts actually receive, which is the failure this rule exists to prevent. It observes the egress facet and the tool budgets so a host can exercise its own redaction filter and its own tool allowlist offline, and two fixtures ship as documented examples because they are the cases hosts get wrong: a generation stream that aborts halfway, and a tool call that fails.
- AIB7. Playground-specific planners and context builders are not public API: they are marked internal and stripped from the published type declarations, or they move into `playground/`. The reason is not tidiness — they are the most copy-pasteable thing in the package, so a host looking for "how do I build a request" finds them and inherits a demo's truncation limits and egress posture as production architecture. What replaces them is the documented integration path — a `ModelAdapter`, the egress facet, and the mock adapter for tests — plus the AI example, enforced by the published API report so there is one supported route rather than an accidental one.

## UC — one edit channel

- UC1. The tool channel is the only edit channel: every durable AI document mutation originates as an `edit_document` tool call, and the coexistence that used to sit beside it is torn down rather than switched off. The `<pen-fast-apply>` XML contract is gone from the tree — stream parser, closing pass, `markdown-fast-apply` / `markdownPatchPlan` runtime, controller bag, plain-markdown fallback, and `context-first` lane — so a model that still emits that markup is talking, not editing, and the `editChannel` option, the `AIEditChannel` union, and `AI_EDIT_CHANNELS` are gone with it: a host that sets `editChannel` gets a compile error, not a silently ignored knob. Keeping the loser dark was considered and rejected, because dark code still costs its tests, its amendments, and every reader who must learn why it exists. Two strategies the first wording of this rule also ordered deleted — `text-fast-apply` and `markdown-full-replace` — were never XML contracts; they were generation-into-a-target strategies that `EC1` permits (selection rewrite and cursor continuation still write text deltas through `openTextStream`; buffered markdown still generates into a target). They did not survive as named strategies either: `AIApplyStrategy` was derived from lane, target, and content format, every consumer read it as one bit, and that bit is now `editsArriveAsToolCalls` on the route (UC5), which is why a rename of those two names never landed — there is nothing left to rename. The literal token `pen-fast-apply` survives in exactly one place: a negative test that feeds the old XML into the stream and asserts the document does not change, which is UC2's evidence and is kept deliberately.
- UC2. No mutation is ever derived from assistant text, and no failure is ever an edit. `EC1`'s fence is unconditional: text deltas exist only for watched generation into streaming targets (`openTextStream` — continuation and selection rewrite), never as an edit plan. The plain-markdown fallback that could answer an XML parse failure by applying an unasked-for full-document replace is gone with its channel. A parse-shaped or schema-shaped failure — a malformed `edit_document` payload included — surfaces as a `diagnostic` event and a refusal result, and the document hash is unchanged; constructing the malformed-payload case and asserting that hash is the pin, because a channel that is broken in both directions would also leave the document alone.
- UC3. There is no structured planner lane, because it was a second text-parsed edit channel: the model emitted JSON in the assistant `text-delta` stream, `parseStructuredPlanPreview` / the plan validator turned it into a mutation, and it landed as a suggestion, which is exactly the durable-mutation-from-assistant-text that UC2 and `EC1` forbid. `runtime/structuredPlanner/`, the `plannerMode` vocabulary (`AIPlannerMode`, `AI_PLANNER_MODES`), `buildPlannerPrompt`, `parseStructuredPlanPreview`, `parseStructuredPlanResult`, `runtime/planExecutor/`, `runtime/planValidation/`, `runtime/reviewArtifacts/`, `runtime/structuredIntent/`, and the structural-review-item surface they fed are all gone from the tree and from `@input/pen-ai`'s public API; `runtime/planTypes.ts` went with them, its one live type `PlanConfidence` dying as `StructuredIntentConfidence` when the adapter registry had no caller left. Block conversion that used to ride a JSON `block_convert` plan now goes through `edit_document` `set_block_props` (`EC18`); `format_text` covers the mark plans. The executor was extracted before deletion was considered, then deleted anyway: both of its supposed consumers — review resolution gated on `planState === "validated"`, and a structured-intent finalize block — were unreachable, so the fence had enclosed a subsystem that could not run, and an extraction without a consumer is a keep in disguise. Previews of a partially-arrived plan are gone with the door; that capability existed only because half-written JSON can be re-parsed on every delta, a tool call arrives complete, and staged edits still surface through suggestions. Markdown prompt assembly lives only in `runtime/flowMarkdown.ts`. Forcing `plannerMode` to `"text"` on the tool-loop lane without providing the `edit_document` replacement is not a substitute for this deletion: it types clean and breaks the live paths that still needed a plan.
- UC4. One staleness authority: working-set view fingerprints (`runtime/viewHashes.ts`, per `EC7`/`EC9`) are the only gate a mutating tool consults. The per-block revision counter (`getBlockRevision`) is gone from edit gating and from the tool payloads; if working-set refresh still needs a change signal it subscribes to commit events. Two authorities that can disagree about "stale" is the defect; the fingerprint — which hashes what the model was actually shown — is the one that matches the channel's addressing model.
- UC5. The route vocabulary is the reachable set, names included, and reachability is proved, not asserted. After the teardown, `runtime/contracts.ts` keeps prompt intent (`PromptIntent`), route lane (`AIRouteLane`: `selection-rewrite`, `cursor-context`, `tool-loop`, `review`), mutation preference (`AIMutationPreference`: `suggestions` | `direct`), mutation mode (`AIMutationMode`), and target kind (`AITargetKind`); a union member with no production consumer is deleted. `AIApplyStrategy` and `AIEditChannel` are gone entirely — the apply-strategy union was derived, not decided, so there was nothing to merge into mutation preference and no `text-fast-apply` / `markdown-full-replace` name left to fix — and the one bit every consumer actually read is `editsArriveAsToolCalls` on the route, true when the lane is `tool-loop`. `AIPlannerMode` and the planner-only members of `AIStructuredLane` went with UC3. The `fast-apply` vocabulary that still ran through commit debug state and session metrics, including public types on `@input/pen-ai` and `@input/pen-react`, folds onto `commit` — the word this codebase already uses for turning generated text into ops — rather than a new synonym; a telemetry surface name is a wire-visible string, so that rename is a release note. The router keeps a property test over the classifiable corpus: every input resolves to exactly one route, and every union member the decision carries is produced by at least one corpus entry — a member no corpus entry produces fails the test and gets deleted.
- UC6. The loop runs tools; tools own their payloads; the controller owns sessions. `agentic/loop.ts` may know that a mutating tool exists and must be forced when an edit is owed (`EC17`); it may not encode any tool's payload shape — the `edit_document` op names, refusal payload, retry shaping, and fingerprint echo live with the tool executor (`runtime/editDocumentPreview.ts`, `runtime/viewHashes.ts`, `@input/pen-tools`), not inlined in the loop. The loop's knowledge of the tool is its name (`AI_EDIT_DOCUMENT_TOOL_NAME`) and the forcing rule; that is the boundary that keeps the next tool from growing the loop again.
- UC7. Reads stay plural; in-editor writes stay singular. The in-editor loop mounts read tools plus exactly one mutating tool (`edit_document`). The single-purpose mutating tools (`insert_block`, `update_block`, `delete_block`, `move_block`, `write_document`) remain in `@input/pen-tools` as the external tool-server contract — skills-lane agents and MCP-style hosts keep them — and must not be mounted into the in-editor loop. The tools README states which surface each tool serves (`## Tool surfaces`); a tool that serves neither surface is deleted.
- UC8. Question intent never touches mutation plumbing. A prompt classified as a question about the document (`PromptIntent` `"question"`) is answered from reads; it must not open a review session, stage a suggestion surface, or force a mutating tool. The claiming test asks a question against a fixture document and asserts zero staged suggestions, zero review sessions, an unchanged document hash, and no `edit_document` call — while the same fixture under an edit prompt produces a staged edit, so the test cannot pass by the channel being broken. The classifier is conservative on purpose: a question misread as an edit rewrites the document, while an edit misread as a question only loses `EC17`'s forced tool choice and still edits when the model picks the tool, which is why opening interrogatives are matched and polite modals (`can`, `could`, `would`, `will`) are not — "Can you make the title purple?" is an edit request wearing a question mark.
- UC9. The published surface does not keep a deprecation window for the deleted channel. `editChannel`, the apply-strategy and planner exports, the plain-markdown fallback, and the revision-counter staleness gate are absent from the current minor; per API7 there is no compatibility shim, and hosts that need the XML channel pin the previous minor. A partial teardown that ships some of those deletions and leaves others on the published surface fails this rule, because the coexistence those leftovers describe is exactly what UC1 tore down.

## RS — one review surface

- RS1. Three surfaces, three jobs, no fourth. The only ways AI content reaches a user's eyes are: (a) the visible stream — `openTextStream` typing into a streaming target the user watches (generation into empty or appended targets, continuation, selection rewrite in direct mode); (b) the autocomplete ghost — the inline completion overlay (`pen-ephemeral-suggestion`), which previews a keystroke-accepted completion, not a document edit; (c) the review surface — streaming preview text while an edit is in flight, staged suggestion decorations once it lands, for every proposed edit regardless of lane. Adding a fourth surface requires demonstrating an edit-presentation job none of the three can express, in a spec amendment, before code. The structured-preview surface (`data-structured-preview-*`, `useAIStructuredPreview`, and the React structured-target preview) is not a fourth job: with UC3's text-parsed door closed it had zero reachable producers, and it is deleted rather than kept alive by adding one. The visible stream and the ghost overlay are explicitly kept: they are not previews of proposed edits — one is watched generation the user asked to land as it types, the other is a keystroke-gated completion — and forcing them through review posture would break both jobs. A presentation-inventory test drives each lane in a headless host and asserts every decoration class and kind is one of the three; an unknown class fails.
- RS2. Every proposed edit rides the review surface. Selection rewrites stage as ordinary suggestions rendered by the review presentation; block generation previews render as streaming preview blocks and then stage. The selection-rewrite bespoke decoration stack and the buffered markdown block preview renderer — two presentation stacks with their own lifecycles, the latter re-staging a whole parsed payload per token — are gone; their staging survives, their presentation does not. The suggest-mode staging interceptor is the single staging authority; the host's mutation preference (`suggestions` vs `direct`) decides whether an edit stages or applies, and has no effect on which surface renders it while pending.
- RS3. Posture is total, including the end of a session. Every state a reviewable edit can occupy maps onto `AIReviewPresentationState` (`user-input`, `ai-writing`, `user-reviewing`, `resolved`) so no reachable state renders nothing: in-flight shows streaming preview text (`ai-writing`), staged work shows accept/reject decorations (`user-reviewing`), an open composer with neither is `user-input`, and a closed, absent, or non-inline session is `resolved`. Accept/reject application is not a distinct presentation member — it is the transition that leaves `user-reviewing` for `resolved`. A generation that ends with edits neither applied nor staged must surface that fact to the host: `isUnappliedEdit` in `controller/unappliedEdit.ts` is the standing obligation, covering every lane that can propose an edit. The receipt alone cannot carry it — `_buildFallbackMutationReceipt` reports `applied` only for committed text, so a successful `edit_document` call and an answer to a question both finish `noop` — and the old guard keyed on `applyStrategy === "markdown-full-replace"` reaching `complete` with a `noop` receipt, which was the signature of a plan that failed to compile and is unreachable now that UC3 and UC5 deleted that channel and that vocabulary. What separates a lost edit from a chat answer is the tool (UC8): the tool-loop reports when `calledEditTool` is true, `editToolAccountedForEdit` is false, the receipt is `noop` or `invalid`, and nothing staged; a refusal, a partial apply, a staged suggestion, or a turn that never called `edit_document` is not a lost edit. The requested-operation path has no tool and no question to mistake it for, so it sets `editAttempted: true` from the fact the host asked for an operation. The generation finishes `error` with `EDIT_NOT_APPLIED_REASON` rather than `complete`, because reporting silence as success is how the channel looks like it ignored the request.
- RS4. One styling contract, exported once. The review surface's class vocabulary is defined in exactly one module — `REVIEW_SURFACE_CLASSES`, `REVIEW_SURFACE_BLOCK_SUGGESTION_CLASSES`, and `REVIEW_SURFACE_CUSTOM_PROPERTIES` in `@input/pen-types` (`constants/reviewSurface.ts`) — because `@input/pen-ai` and `@input/pen-dom` both emit these classes and are siblings, and API3 admits frozen constants, so the contract layer is the only legal shared home. `@input/pen-ai`'s main entry re-exports all three so a host following the review functions does not have to know the contract-layer home. The default sheet ships as an exported string, `PEN_REVIEW_STYLESHEET` from `@input/pen-dom`, rather than a `.css` file, because `sideEffects: false` (API7) lets a bundler drop a bare stylesheet import, and a stylesheet a bundler is entitled to discard is not a contract; selectors interpolate the vocabulary, so a renamed class cannot leave the sheet pointing at a name nothing emits. `PEN_REVIEW_STYLESHEET` cannot legally re-export from `@input/pen-ai`: API1 forbids an extension depending on a renderer, and `@input/pen-ai` does not depend on `@input/pen-dom`. A host styles the review surface by importing the class and theme tokens from `@input/pen-ai` and adopting the sheet from `@input/pen-dom`. Hosts theme by setting the `--pen-ai-review-*` custom properties; they do not re-implement rule blocks. SEC2 refuses `style` on decoration attributes, so a class is the only hook that survives to the DOM and every custom property written as an inline style is inert. Producer sites — suggestion decorations, streaming-preview virtual decorations, streaming-preview delete decorations, context decorations, and `field-editor/reconcilerMarks.ts` — import the vocabulary instead of retyping the strings. The playground adopts the exported sheet plus property overrides; both binding styling docs (`packages/rendering/react/STYLING.md`, `packages/rendering/vue/STYLING.md`) point at the same contract.
- RS5. Preview text is plain text with no control tokens. The streaming preview renders exactly what will land — already verified for the tool channel — and no marker vocabulary survives the XML teardown: `MARKDOWN_FAST_APPLY_OMISSION_MARKER` and any other channel-control token died with `<pen-fast-apply>`. A preview that needs to say "content omitted here" says it through the presentation layer's own affordance, never through magic strings in the payload. The preview is not a re-staged parsed payload per token: markdown still arriving is normalized the same way the commit will parse it (`streamingPreviewInput.ts`) so fences and annotations the accept path drops never flash on screen.
- RS6. Preview fidelity is a property, not a visual judgment: for every corpus edit, the text the preview showed equals the text accept applies, per operation. That is what made the tool channel's preview honest, and it has to keep holding as every lane that proposes an edit rides this surface (RS2). `rs6.previewFidelity.test.ts` holds it over the edit-channel reference corpus in both postures: after each operation of a streamed `edit_document` call has arrived, it composes the preview's virtual inserts and hidden ranges into the visible document, applies the same operations to a fresh copy, and compares the two — per block for single-block operations and as the whole visible document otherwise — and a hidden range the composition did not consume fails the test, so it cannot pass over nothing; so does a frame whose accepted text needs something removed while the preview hid nothing. Hand-written expected strings (`reviewPresentation.streamingPreview.test.ts`) stay as presentation pins, but they could not catch a change that alters preview and apply consistently, which is why the comparison runs against an actual apply. The preview maps each operation to what it changes: replace and delete cover every block they name, ordered by nested document order so blocks inside a container are named like top-level ones, a delete hides its blocks whole rather than leaving empty lines, a replace hides an empty block at its range edge that does not show the replacement text (it has no text to strike, and accept removes it), an insert previews on the side its placement names, offsets are logical (N6), and moves, formatting, and prop changes preview no text — so once a move is among the operations the document is compared as a set of lines rather than in order. An operation whose content has finished arriving previews as finished: a replacement shorter than the text it replaces hides the old tail instead of waiting for text that is not coming.
- RS7. The host-facing `BlockSuggestion` action union is the runtime set. Suggest-mode stages `split-block` (from `pen.splitBlock`) and `format-text` (from `format-text` ops) as review items a host reads through `readAllSuggestions` / `getSuggestions`, so both actions are host-reachable. The contract-layer `BlockSuggestion` on `@input/pen-types` therefore admits those actions and a `format` previousState, matching `PersistentBlockSuggestion` on `@input/pen-ai`. `@input/pen-ai` re-exports `BlockSuggestion` so a host following the review functions gets the same type; `PersistentBlockSuggestion` remains the runtime item (`kind` and `blockId` added). A host exhaustive switch on `BlockSuggestion["action"]` fails compilation when a variant is unhandled (API10). The pin is that `Exclude<PersistentBlockSuggestion["action"], BlockSuggestion["action"]>` is `never`, and the same action keys enumerate `REVIEW_SURFACE_BLOCK_SUGGESTION_CLASSES`.

## Retired

No `AIB`, `UC`, or `RS` member is retired. AIB1–AIB7, UC1–UC9, and RS1–RS7 are all live. One surface element was removed rather than a rule: the `editor` field left `PenStreamRequest.context` under AIB2 and is kept out by a type assertion in `aib2.bounds.test.ts`.
