# Document Durability And Schema Evolution

Most Pen rules describe what happens while an editor is open; these describe the years afterwards. This document owns the stored document as a long-lived artifact: its format identity, what load does with each document state, what happens to content the current schema does not understand, how a host evolves documents across releases, and how growth is bounded and reported. It governs `packages/crdt/yjs`, the schema and load paths in `packages/core`, the persistence and metadata contracts in `packages/types`, and the durability fixtures in `packages/tooling/test`.

## DUR — Document durability and schema evolution

- DUR1. Every Pen document carries a store-generation stamp in `metadata` under the reserved key `penFormat` — `{ format, minReader, writer }`, written by `packages/crdt/yjs/src/formatStamp.ts` — set when the document is created and refreshed on the first write of each session, with refresh skipped when the stored stamp already matches so a freshly created document does not emit a second stamp transaction on its first user write. A document with a missing or malformed stamp is legacy-by-absence, treated as `{ format: 1, minReader: 1, writer: "unknown" }` and stamped on first write, never treated as corrupt. `format` and `minReader` describe the store and not the schema, so adding a block type bumps neither and raising `minReader` requires a store change that genuinely breaks older readers; the reserved `metadata` keys (`penFormat`, `documentProfile`) are a closed Pen-owned list, and every other `metadata` key belongs to the host and is preserved verbatim.
- DUR2. Load resolves a stored document into exactly one of three outcomes: `ok` — well-formed shared types and `minReader` no greater than the reader's format — loads with no diagnostics; `repaired` applies the validator's repairs, names each one in a diagnostic, and emits `crdt:recovered` with `method: "repair"`; `unreadable` throws a typed `PenDocumentUnreadableError` carrying the stamp and the reason. Only a `minReader` above the reader's format or a shared root present with the wrong Yjs type is unreadable, and unrepairable block-level faults still load and emit a named diagnostic; `unreadable` throws rather than degrades because a half-loaded document turns into data loss on the next save, and that is the deliberate exception to the repo's non-fatal posture. Repair is on by default and is a documented load option rather than hidden behavior, the diagnostic list is the API so a host can alert, snapshot, or refuse instead of discovering a silent rewrite, and `crdt:recovered` carries `method: "repair"` from load and `method: "snapshot"` from history snapshot restore and nothing else. The orphan repair re-homes only a block that sits in no `blockOrder` entry and no live block's `children` array — the placement core's orphan re-home reads (COL4) — because a `children`-array child is deliberately absent from `blockOrder` (RI6), and an earlier root-only check appended every nested child of an ordinary saved document to the root order on every load, putting it in two arrays and reporting the load `repaired`; a `parentId` child is stored in `blockOrder`, so one missing from it is unreachable and is re-homed with its `parentId` kept, which restores its route. Re-homed ids are appended in code-unit order, so every peer loading the same state writes the same repair, and the duplicate entries concurrent repairs meet as are removed by the next load or normalization pass. A container's inline title in `content` beside its `children` array is one content shape, not two, and loads with no `INVALID_BLOCK_STRUCTURE` diagnostic.
- DUR3. Preservation is the default at every layer: an unknown block keeps its type, props, content, and children through load, normalization, re-encode, copy, and JSON export, renders through a documented non-editable fallback, and can be selected, moved, and deleted but not edited in place. Both built-in registry factories configure `onUnknownBlock` to passthrough and emit a `schema-unknown-block` diagnostic once per type per editor session; `"drop"` remains available as a host's explicit choice, because the difference between a host deciding to discard content and a library discarding it quietly is the entire point. Unknown props and unknown marks are preserved by the same rule — prop stripping removes values equal to a current schema default and never keys the schema does not know — and apply still refuses to insert or convert to a type the registry does not declare, since that refusal is about new ops and never about existing content.
- DUR4. Pen ships the migration runner and the ledger while hosts ship the migrations: `runMigrations(editor, migrations)` executes each `DocumentMigration` through `editor.apply` with `origin: "migration"`, an origin undo does not track by default, so a user pressing Ctrl+Z after opening a document cannot undo an upgrade. Applied ids are recorded in `metadata`, which makes running the same list twice a no-op and lets a partially migrated document resume correctly; a migration that throws leaves its own ops unapplied in its own transaction, does not block the rest of the list, and appears in the report's failed entries. The same function runs in a browser on load and headlessly over a batch of documents, so a host's batch job and its runtime upgrade cannot disagree, and Pen neither infers migrations from schema diffs nor ships migrations for host block types.
- DUR5. `validateProps` runs at the apply boundary for `insert-block` and `update-block`, on the props those ops carry — not over the whole document and not on every commit. It coerces where the prop schema defines coercion, clamps where it defines bounds, and falls back to the default with a `prop-invalid` diagnostic where a value cannot be salvaged; keys the schema does not declare pass through untouched, and a single-prop update is validated as one key rather than expanding to the rest of the schema. `override()` that patches `propSchema` without passing `validateProps` regenerates that validator from the merged `propSchema` so apply and `schema.resolve` cannot disagree; an explicit `validateProps` on the patch is used as-is. Ingestion paths (import, JSON, XML, clipboard) reach the same validation because they build ops and go through apply, which is what removes the last reason for a second validation dialect; a generated validator with no runtime caller is deleted rather than kept, because it reads as a guarantee in every schema definition a host writes.

- DUR6. The `gc: false` default stays, because reliable restore of deleted content is a shipped feature and silently trading it for storage would be the wrong default; what Pen owes is that the cost is stated rather than discovered. Pen reports growth instead of managing it, emitting a `document-size` diagnostic on load and on a bounded cadence thereafter carrying encoded byte size, block count, and whether GC is enabled, and the docs carry one compaction page written from what is true: merging updates compacts an update log and not tombstones, snapshot rotation reclaims space at the cost of restoring pre-snapshot deletions, and `gc: true` reclaims the most and gives up old-deletion restore. `PenPersistence.compact()` stays in the interface as a host-implemented hook that Pen never calls and says so, and payload-side growth is bounded where it enters by the ingestion caps in IOP4 and IOP5, because a multi-megabyte pasted image in a `gc: false` document is a durability problem created at paste time.
- DUR7. Durability is tested against stored bytes rather than in-memory documents: a corpus of committed binary fixtures — one per released store generation and per notable shape (nested blocks, tables, subdocuments, an unknown block type, unknown props, an emoji and right-to-left text sample) — lives in `packages/tooling/test` and is loaded by CI on every PR. The standing assertion for each fixture is load, repair if needed, normalize, re-encode, then semantic equality against the recorded expectation including `apps`, `metadata`, unknown props, and marks, because the fields a document-equality helper skips are exactly the ones this document is about. Cross-version and migration scenarios are fixtures rather than hand-built documents — an unstamped document loading and being stamped, a `minReader` above the reader's format failing with `PenDocumentUnreadableError`, an unknown block type surviving load, normalize, JSON export, and JSON import intact, a migration list applied twice producing one set of changes and one ledger entry, a failing migration leaving the document consistent and the report accurate, and a migrated document matching between the browser and headless paths — and fixtures are regenerated only by an explicit script with a recorded reason, since a corpus that regenerates itself on failure tests nothing.

## Retired

No `DUR` member is retired. DUR1–DUR7 are all live. One surface element was removed rather than a rule: the `"reimport"` method left the `crdt:recovered` event signature under DUR2, because no path could honestly emit it.
