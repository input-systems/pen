# Scale Envelope And Anchor Performance

SCALE governs how Pen behaves as documents, extension stacks, and sessions grow: the envelope a host can design against, the cost of a single commit, what the benchmarks measure, memory over a long session, and the host-windowing contract. PG1 is the performance contract for anchors. Pen does not virtualize — a host that needs a larger document windows blocks itself, and SCALE5 is the contract for doing that correctly. Frame-level scheduling budgets belong to SCH in `spec/rules/dom.md`; the workloads, published envelope table, committed baselines, and gate scripts live in `packages/tooling/bench` (see `spec/packages/tooling/bench.md`).

## SCALE — scale envelope

- SCALE1. One published table states the tested envelope — block count, longest single block, nesting depth, table dimensions, and concurrent peers — alongside the browser support floor, and every cell is a number that a bench or conformance suite actually exercises. Every number carries its grade: verified (a suite asserts behavior at that size on every run), measured (a benchmark records it, with no pass/fail on the clock), or untested above (the honest ceiling). The table is derived from the suites rather than asserted independently, so raising a number means raising a fixture; it also names what degrades first past the ceiling and refers to SCALE5 rather than repeating it.
- SCALE2. The commit path's work is a function of the change, not of document size or extension count: for a single-character insert into a document of M blocks with N extensions installed, the work is proportional to the affected blocks, not to M, and not to N beyond a cheap per-extension interest check. Decorations are dirty-scoped through the scoped form of a `decorationsFacet` source (`scopedDecorationSource`): for each commit the source declares which blocks to recompute — the commit's `affectedBlockIds` by default, none, or all — and is called with exactly those blocks, so a source that declares no interest in a commit is not called. Blocks no source recomputed keep their decoration list by identity, the decoration set and its generation are kept when nothing changed, and `decorationsChange` fires only on a change and names the blocks whose lists changed. The function form is interested in every commit and is recomputed in full, so first-party extensions use it only where its cost is proportional to the extension's own state — presence, a visible completion, a stream frontier — rather than to the document; `pen/no-unscoped-decoration-source` holds that list in `scripts/unscoped-decoration-source-allowlist.json`. Remote and undo commits are held to the same rule: their affected blocks are the ids the transaction inserted, removed, or changed, read from the `blockOrder` delta rather than the whole order, so a peer's insert bumps one block revision. A structural commit advances the indexes it would otherwise rebuild by what it touched — the change-summary block index and the normalizer's pass index by the transaction's array deltas and the block maps it names, `documentState`'s root order, positions and nested preorder by the `blockOrder` delta, and its parent and child indexes and preorder by the `children` arrays the delta names — and reads the text of no block its summary does not name; the block executors resolve positions through the pass index rather than scanning `blockOrder`, and the DUR3 unknown-type sweep runs after a load and otherwise checks only the blocks a remote or undo commit stored or retyped. An edit inside a `children` array — an Enter, insert, move or delete inside a container — re-reads the named arrays and re-walks only the edited containers' subtrees in the preorder. Three cases still re-read the whole order, each until the next rebuild: a document that lists a block in two entries or on both nesting routes (COL4, RI6) rebuilds the summary and document indexes until normalization repairs it, as does a commit that leaves a `parentId` child in no array (COL4), whose place among its parent's children the full build decides, and a commit the normalizer wrote into without owning its transaction rebuilds the pass index. A pass outside an apply — `normalizeAll`, or a streamed block's deferred normalization when the stream closes (ST3) — runs in a `system`-origin transaction the normalizer owns, advances the pass index at each write as an apply's pass does, and is not advanced again by that transaction's delta. The renderer's side of a structural commit follows the same rule: `documentState.rootBlockIds()` keeps the top-level list by the commit's root edits rather than re-filtering `blockOrder`, the block notifier reads root positions from it and its cached parents from a child-to-parent map kept as snapshots change, drops unsubscribed snapshots from the set it recorded them in, and re-segments only the segments a sibling list's changed span and the runs walked around it reach. Position lookups after an edit replay the edits since the positions were exact rather than scanning the list (`PositionedList`), the normalizer's pass index resolves `after` / `before` positions the same way, and a removal reads no array for a surviving duplicate unless the index lists the id twice. What stays proportional to the order on such a commit is native array moves and copies (a splice, the fresh `rootBlockIds()` / `blockOrder` array, the notifier's segment list) and Yjs's own array event. Normalization Rule 10 (a deleted block's `parentId` children are promoted) reads the blocks a `parentId` index lists under the deleted id — built on the first delete, advanced by every transaction's delta from the block maps and props it names — plus the blocks the open transaction's ops and pass touched since the last observed commit, never every stored block. `JSON.stringify` is banned as a change-detection mechanism in per-commit and per-render paths; signatures come from the summary's identity and version counters instead. The gate is `pen/no-json-stringify-signatures` over `@input/pen-core` and the rendering packages; wire-format / display / clone sites live in `scripts/json-stringify-allowlist.json`.
- SCALE3. The benchmark set includes the configuration hosts ship: a keystroke in an envelope-sized document with a realistic extension stack, measured twice: once with the default preset plus no-op stand-ins named AI, suggestions, autocomplete, search, and multiplayer, which isolates extension-list dispatch, and once with the real `aiExtension` holding staged suggestions and the real `searchExtension` holding an active query, which measures the providers hosts ship. The realistic variant's gate is a count baseline of document reads per keystroke (`packages/tooling/bench/baselines/scale3-realistic.counts.json`); its clocks are recorded and not gated. Each benchmark declares the single axis it isolates — document size, extension count, decoration count, remote-caret count, synced-peer count — and the set covers each axis at two points or more, so a regression report can name the axis that moved. Baselines are committed per benchmark with the machine class that produced them and are updated only in a change that says why; benchmarks run in their own CI job, isolated from the parallel test run, and are compared against the committed baseline rather than against an invented absolute target.
- SCALE4. Every cache in a hot path declares its bound: a maximum entry count, a TTL, or a lifetime tied to a document or editor object, where a `WeakMap` keyed by a DOM node or an editor is a bound and needs no number. `editor.destroy()` releases everything the editor allocated — caches, indexes, decoration sets, undo stacks, field editors — and a standing assertion proves that a destroyed editor retains nothing. A nightly soak scenario (thousands of edits, undo/redo cycles, remote updates, AI streams, mount and unmount cycles) samples heap and reports it as a trend rather than a gate, with one hard assertion: heap after a full teardown-and-recreate cycle returns to within a stated multiple of the baseline.
- SCALE5. Pen does not window blocks and exposes no `virtualize` prop; a host that needs a larger document windows blocks itself. The contract is that any block holding neither the active field editor nor an active selection endpoint may be unmounted; while unmounted its document state is untouched and its decorations are computed but not rendered; selection targeting an unmounted block parks its projection on `(record version, block)`, asks the host's mount requester (`FieldEditorImpl.setMountRequester`) to mount that block in the same turn, and projects in the turn of that block's mount ack (P4); if the first scheduler flush after the park ends with the projection still parked, `selection-target-unmounted` (level `warn`, with `version`, `blockId` and `mountRequested`) is emitted once for that park, and the park stays so a later ack still projects. A host window that honours the request never sees the diagnostic; one that ignores it, or drops a block holding a selection endpoint, always does; and the host does nothing on remount, because reconciliation is idempotent. One conformance scenario exercises the contract end to end — window a large document, scroll it, edit inside the window, and move selection to a block outside it, asserting document correctness and the expected diagnostics — and the docs carry a minimal host-windowing example.
- SCALE6. Renderer work per interaction is a function of the blocks the interaction changed, not of document size. A keystroke, a caret move, or a selection extension re-renders (React, Vue) or re-syncs (the vanilla `mountEditor` tree) only the blocks whose own state changed — text, props, decorations, selection membership or endpoint, field-editor focus, composition — and a mounted surface holds the same number of editor-level subscriptions whatever its block count, because per-block state reaches components through one block notifier per field editor in `@input/pen-dom` rather than through per-block `editor.on` listeners. The gate is the Chromium `scale-render` baseline in `@input/pen-conformance` (`baselines/scale-render.*.chromium.json` with `scale-render.invariants.json`): at 5,000 blocks a keystroke and a caret move within a block render one block, a caret move across a block boundary and a one-block extension each render two, Enter renders at most three plus the renumbered tail of a numbered run, and listener counts, document-read counts, and per-keystroke geometry counts match between 1,000 and 5,000 blocks. Clocks recorded beside those counts are never compared (CH8).

The published table is `packages/tooling/bench/ENVELOPE.md`, generated from `packages/tooling/bench/baselines/envelope.json`. It records block counts of 100, 1,000, and 5,000; a 100,000-character single block; nesting depth 10; a 50 × 20 table (1,000 cells); and concurrent peers verified at five and measured at two, with every axis untested above its top rung. Verification for the ladder is headless, and renderer rows sit beside it: `@input/pen-conformance`'s `scale-render` scenario mounts generated mixed-block documents of 1,000, 5,000, 10,000, and 50,000 root blocks on React, Vue, and vanilla in Chromium, verifies the mounted block count at 1,000 and 5,000 blocks on every conformance run, and records mount time and keystroke-to-frame with a Pen-removed floor, graded measured. The concurrent-peer grade is survival of every peer's insert on every peer rather than peer-to-peer equality alone, because independently populated documents can converge on the same lost `Y.Text`; the measured row's count is the number of peers that observed every insert, not a constant. Past the ceiling, full-document mount and the renderer's side of a structural commit, which stay linear in block count, degrade first.

The envelope is a quiet-machine record: counts are the durable measure and fail on drift on every machine class, while the wall clocks are a `macos-arm64` sample recorded at load 4.45 on 14 CPUs on 2026-10-02 and are compared only within a machine class, gated at `max(attributedP50Ms * 3, attributedP50Ms + 1)` for rungs whose attributed median reaches 0.5ms; at that record every rung, 5,000 blocks included (0.23ms), sits below that signal, so the clocks are recorded and only counts gate. The realistic-stack keystroke baseline `packages/tooling/bench/baselines/scale3.json` records a 0.04ms p50 at 100 blocks and 0.06ms at 1,000 blocks, with eight added no-op decorating extensions at 0.06ms, 256 decorations at 0.05ms, and eight remote carets at 0.06ms — the SCALE2 evidence that extension, decoration, and remote-caret count do not move per-keystroke cost. The realistic variant's first record (2026-10-02) showed what the stand-ins hid: one keystroke performed four whole-document walks and read every block's `Y.Text` four times, three from the AI review provider and one from the search query's rescan, reaching 13.87ms at 5,000 blocks on a loaded `macos-arm64` machine. With the review and search sources scoped, the committed counts are equal at 100, 1,000, and 5,000 blocks — no document walk and six full text reads, all of the edited block. Remote-caret count is eight `data-pen-remote-caret` decorations on one editor; synced-peer count is real forked `Y.Doc`s at 2, 4, and 8 peers, each with the real `multiplayerExtension`, gated on counts per keystroke (deliveries, remote commits, blocks per remote commit, remote carets on the typist, peers observing the keystroke; `packages/tooling/bench/baselines/scale3-peers.json`), with its typist and fan-out clocks recorded beside an empty-relay floor and not gated. `packages/rendering/react/VIRTUALIZATION.md` carries the host-facing form of SCALE5.

## PG — anchor performance contract

- PG1. Anchor cost is bounded on the 10k-word fixture: mint p95 ≤ 5µs per anchor, cold resolve p95 ≤ 1ms for 1,000 anchors resolved in one read phase, cached resolve (AN8) p95 ≤ 50µs for 1,000 repeat resolutions within one commit, repair (AN14) p95 ≤ 0.5ms for 1,000 live anchors on a structural commit, and the selection authority's per-commit resolution work adding ≤ 0.1ms p95 to commit-pipeline phase 6. Those µs and ms lines are recorded bounds rather than enforceable thresholds, because they are machine-dependent and encoding one as a CI threshold gates the runner instead of Pen. What is enforced is the count artifact `packages/tooling/bench/baselines/v3-anchor-budget.chromium.json`: `pnpm --filter @input/pen-bench run bench:anchors:compare` fails by name on a cardinality change, fails on a missing baseline, and fails on a zero-row file, so it cannot pass over an empty set.

The committed artifact records encode sizes of 4/6/6/6 bytes for `clientID: 0` only, mint at roughly 0.39µs, and 1,000 cold resolves in 0.15ms, with the harness floor subtracted. Those are Node figures rather than browser figures and the artifact says so; the Chromium scenario asserts the same cardinalities against `editor.anchors`. Cached resolve, repair, and the phase-6 delta remain unmeasured, which the artifact states rather than defaulting them to green. The count set includes a table-cell cohort because a cell's text is a nested `Y.Text` at `tableContent[row].cells[col].content` while a table block has no `content` key at all — a different substrate, not a size variant — and there is deliberately no cell analogue of the split benchmark, since splitting a table cell is a validated no-op.

## Retired

The `virtualize` prop on the renderer editor components, including its `mobileOverscan` option, is deleted. It was accepted and discarded, and an inert prop tells every consumer who reads the type the opposite of what SCALE5 decides.

The absolute µs and ms figures inside PG1 are retired as enforceable thresholds and survive as recorded bounds only; the enforced gate is the count artifact named in PG1.
