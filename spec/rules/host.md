# Host Integration Rules

Two families share this document. `HOST` owns the contract between Pen and the application that embeds it: module-graph safety, framework client boundaries, the declared runtime floor, feature detection above that floor, server rendering, and the styling contract. Pen's own tests always run in the environment Pen was written in, while every environment a consumer ships into — a React Server Component build, a server-side render pass, an older Safari, a phone on a plain-HTTP LAN address — is a separate promise. These rules exist to make each of those promises testable rather than asserted, which is the difference between a library that works and a library that works here. Pen ships no polyfill bundle, no required stylesheet, and no CSS-in-JS dependency; it detects and degrades, and the floor tells a host which polyfills to bring. Renderer mounts adopt a small field-chrome sheet by default so the golden path is usable; that is not a product theme, and `chrome={false}` is the unstyled path HOST6 tests.

`HB` owns the surfaces through which Pen reaches those applications: the React and Vue bindings, the vanilla DOM path, the headless path, `packages/pen`, `examples/*`, `packages/docs`, the playground, and the transports. Binding size differences are not themselves defects — React carries headless primitives and the reference feature set — but an undeclared difference is how a parity gap ships silently. The capability matrix is the parity instrument; Vue reaching React's component count is not a goal.

## HOST — host integration

- HOST1. Every module in `@input/pen-react` that a consumer can import and that uses React client hooks carries `"use client"`, placed on the package's entry points and on each subpath entry rather than scattered per component. The build must preserve the directive in both ESM and CJS output, and that is a build-output assertion rather than an intention: the gate greps `dist/`. `@input/pen-vue` needs no directive but documents the same client-only mount stance, while `@input/pen-core`, `@input/pen-types`, and the non-rendering extensions stay directive-free and importable from server code — which is what HOST2 protects.
- HOST2. No published module touches `window`, `document`, `navigator`, `matchMedia`, `localStorage`, `getComputedStyle`, or `requestAnimationFrame` at module scope; browser access happens inside functions, effects, or lazily-initialized accessors, enforced by the `no-module-scope-browser-globals` lint. Import safety is tested rather than asserted: a smoke suite generated from the manifests imports every path in every published `exports` map in a plain Node process with no DOM globals and fails on any throw, and because it is generated, a new package or subpath is covered the day it exists. The same suite asserts that `createHeadlessEditor()` constructs and applies ops in that process, which turns the headless claim into a test instead of a hand-verified habit.
- HOST3. Every published package declares `engines.node` matching what CI verifies, and CI runs a matrix across the declared range's endpoints rather than only the version the maintainer uses, because a floor is a promise. A single browser-support table is published in the README and the docs site and is the normative floor for the whole workspace: minimum Chromium, WebKit and Safari, and Firefox versions, with the EditContext-versus-contenteditable backend split stated per browser, since that split materially changes input behavior. The floor is derived from the features the code actually needs — HOST4's allowlist is the inventory it comes from — rather than chosen aspirationally; raising it is a minor-version change with a changelog entry, and lowering it never happens silently. `spec/` and the docs site state the floor identically: one number, one place, referenced everywhere else.
- HOST4. Above the floor, detect; at or below the floor, use freely, because a guard for a guaranteed feature is noise. Any web API newer than the HOST3 floor is used behind a feature test with a defined degraded path and a documented consequence for the user, and the inventory of above-floor APIs is a lint with an allowlist (`scripts/above-floor-api-allowlist.json`, rule `no-above-floor-api`) where each entry names its fallback — that list is what the HOST3 floor is derived from, which keeps the two honest about each other. ID generation in library code goes through one helper (`generateId`) that owns the feature test and the fallback, and bare `crypto.randomUUID()` calls in published packages are banned by the `no-bare-random-uuid` lint: a missing UUID API may degrade ID quality but must never prevent constructing an editor, including on a non-secure origin such as plain HTTP to a LAN address. Library-authored inline styles and stylesheets either sit at the floor or carry a fallback declaration in the same rule (`background: <fallback>; background: color-mix(...)`); a visual nicety may degrade, but a highlight that vanishes may not, so the AI review surfaces in particular must stay visible without `color-mix()`.
- HOST5. Server rendering has a stated contract, and the choice is shell-only SSR: the server renders the editor container and no document content. That is deliberate rather than accidental, because faithful SSR of a CRDT document requires the document on the server and Pen does not own that transport. A host needing indexed content renders it from its own copy of the document through the DOM-free HTML export surface rather than from the editor, and the docs show that pattern — the difference between "SSR is unsupported" and "SSR renders a shell, and here is how you get content into HTML". Layout effects run through one `useIsomorphicLayoutEffect` seam so a server pass produces zero React warnings, and zero is the gate because hosts read warnings as bugs regardless of who caused them; hydration is tested with both an empty and a non-empty document, asserting no mismatch for the shell.
- HOST6. Pen is headless: it ships no required stylesheet, and an editor with no CSS is functional — editable, caret visible, blocks laid out by the host. Functional includes an empty document, which is the case that separates a stated contract from a tested one: without chrome, an empty `[data-pen-inline-content]` has zero width, so pointer activation resolves the clicked `[data-pen-editor-block]` rather than only the inline span, and a host is not required to supply a `min-width` to land the first keystroke. That unstyled path is `chrome={false}` on `EditorRoot`, `PenEditor`, and `mountEditor`, and the conformance harness at `/?unstyled=1`. The golden path is the opposite: those mounts adopt `PEN_EDITOR_CHROME_STYLESHEET` from `@input/pen-dom` by default so `createEditor()` plus `<PenEditor />` is a usable field — the inline surface fills its block, empty placeholders paint when the renderer sets `data-placeholder-visible`, and `:focus-visible` uses `--pen-focus-ring` (default `Highlight`) after dropping the UA shrink-wrap ring (AX5). The sheet is exported text, not a `.css` file, because published packages set `sideEffects: false` (API7). Where the library must style something for correctness rather than taste — caret overlays, selection highlights, focus rings (AX5, with overlay carets staying `aria-hidden` per AX7), suggestion decorations, and text entry whitespace (RI5, where collapsing a stored `\n` or a repeated space would lose a document character rather than restyle it) — it does so through inline styles, that adopted sheet, or a documented, overridable custom-property surface, and every custom property the library reads is documented with its default and its purpose, canonically in `packages/rendering/react/STYLING.md` and `packages/rendering/vue/STYLING.md`. Boolean `data-*` attributes are presence-only: `true` emits the valueless HTML form (`data-readonly=""`), `false` and `undefined` omit the attribute, hosts style with the bare selector `[data-readonly]`, and `buildDataAttributes()` in `@input/pen-dom` is the single producer, re-exported by `@input/pen-react`; off must be absence rather than a false-y value, and ARIA booleans are exempt from this convention because they stay the literal strings `"true"` and `"false"` — `aria-hidden=""` is invalid and matches nothing.
- HOST7. The document Escape selection ladder is a bubbling default, not a capture-phase claim. Overlay and host chrome that want Escape register in the capturing phase and call `preventDefault`; the ladder yields when `defaultPrevented` is set. The ladder must not `stopImmediatePropagation` during capture — that is what made a later-mounted menu lose the key while the caret collapsed to a block selection. This is not a slash-menu or suggestion-menu special case: any host overlay has the same problem. S4 forbids solving it with a timer, retry, or suppression flag.
- HOST8. Block-selection Enter is a bubbling default, not a capture-phase claim, for the same reason as HOST7. A host that owns Enter on a structural block registers a listener on the editor element and can `preventDefault`; the document handler yields when `defaultPrevented` is set. The handler must not `stopImmediatePropagation` during capture — that is what forced hosts onto `window` capture, the only phase that still ran first. Arrow keys, Backspace, Delete, Tab, Mod-a, and history shortcuts stay in capture; they are enumerated so a later host that needs the same yield files a named follow-up rather than rediscovering document-capture by accident. S4 forbids solving it with a timer, retry, or suppression flag.
- HOST9. While a block or cell selection is active, DOM focus stays on the editor's focus sink whenever the editor already owns focus or focus has fallen to the document body. A host can therefore attribute a keystroke to a specific editor by containment (`root.contains(event.target)` / `root.contains(document.activeElement)`). Focus is not stolen from a native text-entry control that is not this editor's field surface — whether that control sits outside the editor root or is nested host chrome inside it (a prompt textarea, a search field). The field editor itself is contenteditable and is not this case. The sink is focused synchronously from `syncFocusSink` in the same `selectionChange` turn; S4 forbids a deferred restore. The same holds for text: while such a native control owns focus, an authority selection write (P1, including `setSelection(null)`) is recorded but not projected, and a decoration change that rebuilds the active field does not write the selection back into it — writing a DOM selection into a field moves focus with it. The record self-heals on the next projection trigger. Gesture and programmatic projections (`activateTextSelection`, `focusTextSelection`) are not gated: a mousedown on the editor runs before the browser moves focus, and `focus()` moves it explicitly first. A host that wants focus to move into the editor from its own input asks for it; a bare `editor.setSelection` never takes it.

## HB — hosts and bindings

- HB1. The capability matrix at `packages/docs/CAPABILITY-MATRIX.md` is the normative per-surface inventory — React (`@input/pen-react`), Vue (`@input/pen-vue`), vanilla (`@input/pen-dom`), headless (`@input/pen-core`) — and a capability absent from it does not exist publicly; changing a cell is a spec-visible change. Each cell opens with one of four statuses: `supported` (works on this surface with the packages the row names, and the named path proves it on this surface), `bring-your-own-ui` (behavior and state reach this surface; the binding ships no components for it, so the host renders the chrome), `not-supported` (not reachable here), or `planned` (intended, not shipped). The fourth status exists because three could not describe a capability that lives below the bindings: calling Vue AI review `supported` would promise an accept/reject component that does not exist, and calling it `not-supported` would tell a host to abandon decorations that already paint; `bring-your-own-ui` is the most common cell, and Vue reaching React's chrome is not a goal. Binding READMEs point at the matrix and summarize their column rather than duplicating cells. `scripts/check-capability-matrix.mjs` (`pnpm capability-matrix`, `.github/workflows/static-analysis.yml`) walks every cell: the status is in the vocabulary, the four surface columns are present in that order, and every claiming cell (`supported` or `bring-your-own-ui`) names a repo path that exists and is not under `playground/`.
- HB2. Bindings stay thin: behavior belongs in `@input/pen-dom`, `@input/pen-core`, or an extension; `@input/pen-react` and `@input/pen-vue` provide subscriptions, components, and framework glue only (API6, CS8). New binding code that could live below the binding must; a binding PR that adds non-glue logic needs the matrix to say why. This is a standing review rule, not a script — CS8's boundary tests pin the first tranche (gestures and atom interactions in pen-dom; optional feature packages as peers).
- HB3. `examples/react`, `examples/vue`, `examples/vanilla`, and `packages/docs` are pnpm workspace members in the turbo `build` graph, so `pnpm build` in CI compiles them and an example that stops compiling fails the PR; their `dist/` outputs are gitignored (`dist/` in `.gitignore`). The docs checkers that cannot live in a Pages-only workflow — DOC2 pages, DOC3 tables, COL5/COL6 — run on `pull_request` via `.github/workflows/docs.yml`, with Pages configure/upload/deploy skipped there. The three examples have `tsconfig.json` but no `typecheck` script, and `vite build` does not run `tsc`, so "typecheck where configured" reaches `packages/docs` only; an example can ship a type error CI does not see.
- HB4. `packages/pen/README.md` states exactly which extensions, schema set, and options `defaultPreset()` assembles — five extensions in resolve order (`tools`, `delta-stream`, `undo`, `rich-text-shortcuts`, `html-clipboard`), each with the flag that omits it, plus `createDefaultSchema()` — and a consumer diffs that list against the capability matrix. `hb4.batteries.test.ts` parses the README table at test time and compares it to `defaultPreset().resolve(…).extensions.map((e) => e.name)`, with no second literal in the test, so README and code cannot drift together. Removing a knob from the assembler updates the declaration in the same PR; a preset that silently re-defaults is how a deleted option comes back.
- HB5. The playground is the reference host, not the proof: every claiming cell in the matrix names a test or example path outside `playground/` that exercises the capability on the surface the cell claims, so a React-binding test cannot vouch for a Vue cell. That is the anti-playground-only-wiring rule — the class of gap where a feature works in the one host its author ran. A per-cell demo app is not required: the three examples are minimal mounts, `packages/docs` mounts no editor, and a Vue-binding test is better evidence than a Vue demo nobody runs. Shared evidence is allowed when the capability has no per-binding API — both bindings mount the same `FieldEditorImpl`, so a DOM-level test can stand for all three DOM surfaces, which the matrix states in prose. The matrix checker enforces path existence and the playground ban; it does not check that the named path is on the claiming surface, so that half of the rule is review, not the script.
- HB6. `@input/pen-transport`'s two variants (`./direct` and `./sse`, `packages/transport`) each document a support status and carry a host-driven integration test (`hb6.hostIntegration.test.ts` per variant) that drives `PenTransport.stream(PenStreamRequest)` into `processStream` rather than a transport internal. Direct is experimental: in-process only, no socket, no resume, `connected` always true, `onConnectionChange` never fires. SSE is reference: it illustrates the protocol with a single-process in-memory handler, and `GET` with `Last-Event-ID` returns 405, so it is not resumable. Neither is `supported`; nothing here carries production guarantees. Two collisions stay stated rather than resolved. HB6's vocabulary is `reference | supported | experimental` while COL6's docs gate already enforces `reference | production | development-only` on the same README, and both variants currently declare a tier in both vocabularies so both gates stay green — a workaround, not a design; one of the two rules should adopt the other's words. And the "keep a consumer" half: no in-tree application imports either transport — not the playground, not the examples, not the starter, not `@input/pen-ai`, which does not take a `PenTransport` at all because `processStream` consumes the iterable directly — so the tests are the only in-repo consumers. The package is not deleted, because it is a published package whose consumers are hosts outside the tree by construction; for a published package that half of the rule collapses into the testing half, and it is not the second independent check the title implies. The remaining gap is the same class HB5 names: no host-shaped application in this repo uses either transport.
- HB7. Public barrels (`index.ts` per published package) export only what the docs and the capability matrix admit; an export that appears in `api-report.md` without a matrix or docs home is the defect. A barrel change regenerates its `api-report.md` in the same PR — the report diff is the reviewable artifact, and CI's `scripts/api-reports.mjs` fails on drift. `@input/pen-ai`'s barrel in particular exports none of the deleted planner, strategy, or `editChannel` vocabulary (`uc3.barrel.test.ts` plus the committed report).
- HB8. A host that `cloneElement`s a default React block renderer to add `extraAttributes` or `data-*` must see those attributes on the same layout host the renderer already paints, and must not be able to break the renderer by doing so. `ParagraphRenderer` and `HeadingRenderer` return that host directly. The three list items share `ListItemLayout`, which spreads loose host `data-*` and then `extraAttributes` onto `[data-pen-list-item-layout]`; the host-facing shape is `ListItemHostAttributes`, exported from `@input/pen-react` because it appears in those renderers' return types. Ownership is decided by write order, not by trust: host attributes land first, then the layout identity attributes (`data-block-type`, `data-indent`, `data-selected`, `data-pen-list-item-layout`) that DOM navigation and library CSS select on, then each renderer's `libraryAttributes` — `data-counter` for numbered items (including a `start` override) and `data-checked` for check list items. A host therefore cannot renumber a list, un-check an item, or relabel a block type through an attribute, and `libraryAttributes` is a renderer-internal prop rather than part of the host contract. A hook-only wrapper such as `NumberedListItemView` is transparent: it forwards host props into that same spread and exists only to call `useNumberedListItemValue`, not as a second attribute surface. Evidence is `packages/rendering/react/src/__tests__/listItemHostAttributes.hb8.test.tsx`. The rule is scoped to the React binding; the Vue list path (`PenBlock.ts`) has no host-clone contract and makes no claim here.

## Retired

No `HOST` or `HB` member is retired. HOST1–HOST9 and HB1–HB8 are all live and govern shipped code. HOST7 was added after a capture-phase Escape ladder, registered when the editor root mounted, stole Escape from later-mounted menus and host overlays. HOST8 is HOST7 one key over: block-selection Enter stayed on document capture with `stopImmediatePropagation` after Escape moved to bubble. HOST9 was added after a block selection left DOM focus on `document.body`, so a host could not attribute the keystroke to one editor and two composers in one document raced for Enter. HB8 was added after `NumberedListItemView` swallowed host `data-*` / `extraAttributes` that `BulletListItemRenderer` already landed on `ListItemLayout`, so alignment and other host-painted attributes failed on numbered items only. Widening that spread exposed the inverse defect in the same family — a host `extraAttributes` replaced the renderer's own prop wholesale, dropping `data-checked`, and could overwrite the layout identity attributes — so the rule covers both directions rather than only the one Input hit.
