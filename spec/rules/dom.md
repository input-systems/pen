# DOM Scheduling, Geometry, And Bidi

These families govern how Pen reads and writes the DOM and how bidirectional text is resolved, measured, and navigated. The scheduling, geometry, and overlay set (SCH, G, OV) is enforced in `packages/rendering/dom/src/scheduler.ts` and `packages/rendering/dom/src/geometry/`, with the framework renderers bound to its paint-plan output rather than measuring on their own. The field-editor set (FE) is the input spine in `packages/rendering/dom/src/field-editor/`: three backends, one lifecycle, scheduler-owned frames, and the table-cell parity contract in `CELL-PARITY.md`. Selection semantics stay in `spec/rules/selection.md` (S1–S6) and `spec/rules/anchors.md`. The bidi and direction set (DIR, BR, M, RI) is enforced in `packages/rendering/dom/src/bidi/` for level resolution and in `packages/core/src/direction/` plus `packages/core/src/facets/directionFacets.ts` for direction resolution and motion semantics.

## SCH — DOM scheduler

`DomScheduler` exposes `read`, `write`, `measureNow`, and a `phase` of `"idle" | "read" | "write"`. One flush runs per animation frame when work is pending: it collects the commits since the last flush plus the current selection record, runs the read phase (geometry cache invalidation, then queued reads in FIFO order), then runs the write phase (renderer DOM updates, queued writes FIFO, the selection projector last so it sees final layout, then overlay paints). A write queued during the read phase joins the same flush; a read queued during the write phase moves to the next flush and emits `diagnostic { code: "read-after-write" }` when it observes layout that write invalidated.

- SCH1. Pen-internal code — the selection projector, overlays, and geometry — never calls `getBoundingClientRect`, `getClientRects`, `elementFromPoint`, or `caretPositionFromPoint` outside a read phase or `measureNow`. The gate is `pen/no-unscheduled-measure` in the root ESLint config, scoped to `@input/pen-dom`, `@input/pen-react`, and `@input/pen-vue`. Allowlisted GeometryReader and justified pre-scheduler sites live in `scripts/unscheduled-measure-allowlist.json`.
- SCH2. `measureNow` is the synchronous escape hatch for command handlers that need geometry during dispatch, such as vertical caret motion. Each call forces a flush boundary and increments a counter surfaced in diagnostics, and the perf budget caps that counter.
- SCH3. The scheduler is per editor root. Multiple editors on a page never share read or write queues.

Budgets, enforced by the conformance perf tests: one flush per frame, and zero flushes when no work is pending, so an idle typing pause produces no scheduler activity; in typing steady state (single caret, 60cps synthetic) at most one `measureNow` per keystroke, with read phase ≤ 2ms and write phase ≤ 2ms at p95 on the 10k-word reference fixture in CI Chromium; eight active remote carets add no layout passes beyond the flush's single read phase. The committed Chromium baseline records a 3.4ms read phase against that 2ms line; the typing-budget scenario now times the production scheduler taken from `getRootGeometry(root)` (FE4), and the overrun is the caret read on the 10k-word fixture rather than a second harness-constructed scheduler, so the budget stays at 2ms rather than being raised to match the measurement.

## FE — field-editor spine

The field editor is three input technologies on one lifecycle: `editContextBackend.ts`, `contenteditableBackend.ts`, and `expandedContentEditableBackend.ts`. `FIELD-EDITOR-BACKENDS.md` is the architecture table; `FIELD-EDITOR-TEARDOWN.md` is the teardown document.

- FE1. One lifecycle spine owns attach, teardown, and listener bookkeeping for all three backends. The spine is two modules because the halves have different lifetimes: `backendLifecycleController.ts` owns which backend exists (create, replace on a surface-mode or element change, deactivate); `BackendAttachment` in `backendAttachment.ts` owns what a backend holds while attached. Backends register through `listen`, `listenDocument`, `listenEditContext`, `observeMutations`, `observeText`, and `subscribe`, and `release()` runs those undos, so teardown is total by construction rather than a mirrored `removeEventListener` block per backend.
- FE2. A backend owns its input technology and nothing else: EditContext owns `textupdate` / `textformatupdate` / `characterboundsupdate` plumbing; contenteditable owns `beforeinput` / composition and the mutation watchdog; the expanded backend owns only what expansion changes (multi-block host, cross-block replace and delete, handoff back to a single-block backend). Clipboard and drag bind once through `bindBackendTransferEvents` in `backendTransferEvents.ts`; inline-decoration lookup is `inlineDecorationsForBlock` in `utils/inlineDecorations.ts`. Code found duplicated across two backends moves to the spine in the same change that finds it.
- FE3. No production module in `@input/pen-dom` outside `scheduler.ts` calls `requestAnimationFrame`. A frame wait that is real scheduling moves onto a scheduler-owned callback; a selection retry in disguise is deleted under S4, not migrated. The two click-outside `insert-block` sites used to wait a frame for a block that was not mounted yet; they now park through the projection controller and the scheduler's P1 slot. Multi-click completion is `scheduler.read` in `contentGesturesPointerSelection.ts`; the inline-atom drag-preview coalescer is `scheduler.write` in `inlineAtomWrapperInteractions.ts`. The gate is `no-restricted-syntax` in `eslint.config.mjs`, scoped to `packages/rendering/dom/src` with `scheduler.ts` excepted, banning both the bare call and any `*.requestAnimationFrame` member form — the scheduler's own call is `globalThis.requestAnimationFrame`, so an identifier-only ban would miss every form a reintroduced site would use. `@input/pen-react` is outside this rule: its overlay and menu primitives own their own frames.
- FE4. Commits reach `DomScheduler.acceptCommit`. The feed is `FieldEditorImpl`'s `editor.on("commit")` subscription, not `mountEditor`: React and Vue hosts construct a field editor without a mount function, so a host-only wire would feed only the vanilla path. The scheduler's next flush invalidates cached rects of the named blocks; without the feed the reader only clears on resize or font load. The typing-budget conformance scenario measures this path: the harness takes reader and scheduler from `getRootGeometry(root)` rather than constructing its own.
- FE5. Pointer gestures split along the three gestures behind `attachContentGestures` in `contentGestures.ts`: `contentGesturesPointerSelection.ts`, `contentGesturesDrag.ts`, `contentGesturesRegion.ts`, plus `contentGesturesShared.ts`. No new concepts. Boundary snap uses `getEditorBlockSelectionRole` rather than a block-type allowlist. Gesture conformance scenarios pin behavior across the split.
- FE6. Table-cell field editing declares its parity in `packages/rendering/dom/CELL-PARITY.md`, with `packages/tooling/conformance/scenarios/fe6-cell-parity.spec.ts` as the net. Grid selection (`selection.type === "cell"`, no field attached) is distinct from cell editing (`activeCellCoord` set); cells always use `ContentEditableBackend`. A capability outside the supported set fails closed — no-op plus, where declared, a diagnostic — never half-works. Mark toggling is the declared-unsupported instance that emits `cell-capability-unsupported` with `capability: "marks"`, and only on the field-editor `beforeinput` `formatBold` route through `DIRECT_HANDLERS` (Chromium and WebKit produce that event inside a cell; Firefox delivers keydown and nothing more, so there is nothing to decline). `richTextShortcutsExtension()` declines via `toggleInlineMark`'s `false` return and emits no diagnostic. The other seven unsupported capabilities still decline silently and are listed with what a host can observe, because a diagnostic on a path the host already handles is noise. Six further capabilities reach a cell only partially — decoration ranges and presence validation are keyed by block id and block-local offsets while a table block's text length is zero — and live in a third table rather than under `supported`.
- FE7. `selectionBridgeOffsets.ts` is the DOM↔model offset mapping (graphemes, inline atoms, mark boundaries) and is property-tested for round-trip identity: model offset → DOM position → model offset, and DOM → model → DOM landing in the same rendered position, over every offset of the fixture corpus, not the ends. The corpus covers plain ASCII, empty, astral pairs, combining marks, a ZWJ family, regional indicators, and atoms alone, at each edge, between text, and adjacent. Atom fixtures use production `createInlineAtomElement`, so the identity claim is about the DOM the reconciler emits.
- FE8. `FIELD-EDITOR-BACKENDS.md` and `FIELD-EDITOR-TEARDOWN.md` describe the spine; a structural change whose docs still describe three parallel backends is not done. `src/a11y/MANUAL.md` stays aligned with live symbols and must not name a deleted file or call `DomScheduler.projectSelection` an empty stub now that the field editor installs the projector.
- FE9. An A5 `origin: "mapped"` `selectionChange` after `editor.apply` writes that caret into the attached EditContext through `updateSelection` and drops `edit-context-textupdate` authority. Ordinary user/textupdate selection writes keep the stamp — it is the last trusted typing caret when EditContext later reports a stale range. `resolveEditContextTextUpdateRange` prefers that authority, so one leftover offset on a now-shorter block is enough for the next `textupdate` to clamp or insert in the wrong place. A host `selectText` after its own `apply` only forces a projection and is not a workaround; the backend owes the sync. S4 forbids a timer or suppression flag on this path.
- FE10. A pointer drag opens a gesture from host chrome, not only from a block. `contentGesturesDrag.ts` resolves the `mousedown` target to a block id and, failing that, falls back to `pointToEditorSelectionPoint` — the nearest block edge in the vertical band (G4) — and marks the gesture `startedInHostChrome`. The fallback is load-bearing rather than a nicety: `mousemove` and `mouseup` are both guarded on an open gesture, so a drag beginning in the content padding beside the column, or on the root next to it, left a collapsed caret instead of a selection even though the pointer window was already open for that target (R2). The flag marks a drag anchor, not a clicked block, so a gesture that never reached a block leaves `mouseup` to the click path, where the click-outside affordance lives: a host-chrome origin changes what a drag does and nothing about what a click does. T2 owns the resulting selection, the single-block case included, since a drag anchored outside the field has no native range of its own to inherit. `packages/tooling/conformance/suites/geometry/host-chrome-drag.spec.ts` pins the cross-block and single-block gestures and asserts the probe lands on chrome rather than on a block.

## G — geometry reader

All measurement flows through one `GeometryReader` (`packages/rendering/dom/src/geometry/geometryReader.ts`) that returns plain data, so no live DOM reference escapes into consumer code. It exposes `caretRect`, `rangeRects`, `lineBoxes`, `pointAt`, `blockRect`, and a `generation` counter that consumers use as a cache key. `rangeRects` decomposes a logical range into per-run rects, so an RTL-embedded range inside an LTR line yields visually correct disjoint rects instead of one wrong spanning rect, and `LineBox.runs` carries `{ run, rect }` pairs in visual order. A host that needs custom measurement writes its own code outside Pen's phases; geometry re-exports no raw DOM nodes.

- G1. Geometry is measured with `Range.getClientRects()` over text nodes resolved through `packages/rendering/dom/src/field-editor/offsetDomain.ts`, never with per-character spans. An atom's rect comes from the atom's host element.
- G2. Geometry is cached per block, keyed by the commit id of the last summary touching that block plus the viewport-resize, font-load, and scroll generations. The read-phase invalidation scan drops entries for blocks named in the flush's summaries, and a `ResizeObserver` on the content root and `document.fonts.ready` bump the global generations. Cached rects are viewport-relative, so a capture-phase `scroll` listener on the root's document bumps the scroll generation — capture because `scroll` does not bubble and a nested scroller inside the root moves cached rects too. A scroll in a container that neither contains nor is contained by the root cannot move the root, and leaves the cache warm.
- G3. `caretRect` at a bidi-run boundary or a line wrap returns the rect on the side named by `affinity`: `"downstream"` is the run or line box containing the position when scanning forward in logical order, `"upstream"` the one found scanning backward.
- G4. `pointAt` resolves a coordinate through `caretPositionFromPoint`/`caretRangeFromPoint` and then snaps to the nearest normal position. Coordinates outside every block map to the nearest block edge in the vertical band, so a click below the document selects the last position.
- G5. Vertical caret motion (`pen.caretUp`, `pen.caretDown`) is computed from geometry rather than delegated to the browser: take `x = goalX ?? caretRect(current, affinity).centerX` where `affinity` is the selection's own (`"downstream"` when absent), never derived from the motion direction — at a wrap or `\n` boundary the two sides are different lines (G3), and measuring the caret on the side it is not drawn on skips a line or, in a single-block document, moves nowhere. From the current line, find the adjacent `LineBox` in the motion direction (same block, else the visually adjacent block by `blockRect` order), and target `pointAt(x, y)` where y is the current caret's centerY if that already falls strictly inside the target line box, otherwise the line's vertical midpoint. Hit-testing the shared edge between adjacent full-width line boxes maps back onto the current block in Chromium and WebKit once default chrome makes the inline surface fill its block (HOST6). Vertical motion stays direction-neutral (M5). `goalX` persists on the resulting selection when that selection stays a text caret. When the measured point's block is not an editable text block, the command escalates to `BlockSelection` and drops `goalX`, except a collapsed caret on a table (N2, T5).

## OV — overlay contract

Overlays — the caret overlay, multiplayer carets, AI decoration outlines, drop indicators, and block or cell selection highlights — are pure functions of records, facet outputs, and geometry snapshots.

- OV1. Overlays subscribe to flushes, not to raw events: they receive `(commits, selectionRecord, reader)` in the read phase, compute a paint plan of plain data, and paint that plan in the write phase. Event-driven painting is not an available path.
- OV2. Overlay DOM lives in the dedicated overlay layer element per editor root, a sibling of content under a `position: relative` root, painted with transforms only and never with layout-inducing properties. It is `pointer-events: none` except for explicitly interactive handles.
- OV3. The React and Vue overlay primitives are bindings over the paint-plan API (`onPaintPlan(cb)`) and hold no measurement code of their own.

## DIR — block direction resolution

A block's direction resolves in order, first hit winning: the explicit `props.direction` prop (`"ltr" | "rtl" | "auto"`, where `"auto"` falls through), the `pen.blockDirection` facet resolvers in facet order (first non-null, which is how a host implements inherited direction such as a reply-quote block taking the quoted mail's direction), the UAX#9 P2/P3 first-strong heuristic over the block's logical text, then the `pen.defaultDirection` facet (single-value, default `"ltr"`). Per-paragraph directionality UI and RTL mirroring of host chrome are host concerns.

- DIR1. Direction resolution is cached per block and invalidated when the block's text or props appear in a commit summary, or when facet outputs change.
- DIR2. Renderers set `dir` on the block's content host element from Pen's resolved direction and never emit `dir="auto"`, because resolution is Pen's rather than the browser's and measurement must agree with rendering.
- DIR3. Direction is per block. Nested blocks resolve independently, so a quote block may resolve `rtl` inside an `ltr` document.

## BR — bidi run resolution

`packages/rendering/dom/src/bidi/levels.ts` implements `computeBidiRuns(text, base)`, returning logical `{ from, to, level }` runs where even levels are LTR and odd are RTL. Remote carets and decorations inherit RTL correctness through `rangeRects` and `caretRect`; no per-feature bidi code is permitted outside `bidi/` and `geometry/`.

- BR1. The implementation covers the UAX#9 rules an editor needs — P, X including the LRI/RLI/FSI/PDI isolates, W, N, I, and enough L1/L2 reordering to produce runs — and is accepted against the committed BidiTest character-class vector subset rather than the full BidiTest suite, which is overkill for run-level output.
- BR2. Atomic inline nodes take Bidi_Class ON (neutral) and always form their own run boundary.
- BR3. Runs are cached with the block geometry cache and share its invalidation (G2).
- BR4. Bidi level resolution lives in-tree with its vector suite and adds no dependency. `Intl.Segmenter` remains the only text-segmentation dependency, for graphemes and words, and is unrelated to bidi levels.

## M — motion semantics

Direction affects which key advances the caret, not how a caret is represented: Pen renders one caret plus affinity and never splits a caret at a direction boundary.

- M1. `pen.caretLeft` and `pen.caretRight` move in logical order regardless of run direction — Right is the next normal position, Left the previous. The names exist for keymap familiarity; there is no visual-order motion mode, because logical motion is stable under editing and never strands the caret.
- M2. In a block whose resolved direction is `rtl`, the default keymap swaps the bindings — `ArrowLeft` dispatches `pen.caretRight` (logical forward) and `ArrowRight` dispatches `pen.caretLeft` — so pressing toward the text's reading direction advances in reading order. The swap is resolved from the focus block's direction at keymap dispatch, and the `extend` variants swap identically.
- M3. `pen.caretLineStart` and `pen.caretLineEnd` are visual: they target the visually first and last position of the line box, so in an `rtl` line LineStart is the right edge and Home/End do what the user sees.
- M4. `pen.caretWordLeft` and `pen.caretWordRight` follow the M1 and M2 semantics at word granularity.
- M5. Vertical motion (G5) is pure geometry and therefore direction-neutral; it has no bidi cases.
- M6. `pen.deleteBackward` and `pen.deleteForward` are strictly logical — backward is the previous logical grapheme — and are never swapped by direction, because deletion semantics track insertion order.

## RI — rendering and input

Exporters emit text as stored: Pen inserts no LRM or RLM direction marks on export.

- RI1. The content root gets `unicode-bidi: isolate` per block host, and marks or decorations must not introduce `bidi-override`. The gate is `pen/no-bidi-override` in the root ESLint config over style objects in the DOM and framework renderer packages.
- RI2. IME composition inside an RTL run needs no special handling beyond the ordinary composition rules: composition owns the field, and geometry reads resume after it ends.
- RI3. Pasted mixed-direction text is plain content. Direction resolution reacts through DIR1 invalidation rather than through a paste-specific path.
- RI4. The overlay caret measures through `caretRect` and so inherits bidi correctness, and the native caret inside the active field agrees because DIR2 sets `dir` on the same element the browser measures.
- RI5. The text entry surfaces the library renders — the inline content host in all three renderers, and the table cell content hosts in React and Vue — carry `white-space: pre-wrap` as a library-authored inline style, on the same style objects as RI1's `unicode-bidi: isolate` and for the same reason: correctness, not taste. A soft break is stored as `\n` in the block's text (`pen.insertLineBreak`) and repeated spaces are stored verbatim, so under CSS's initial `normal` the browser collapses both and a character the document contains becomes invisible and unreachable — the caret does not move, while undo and delete still count it. That is a defect HOST6 does not license a host to fix, because an editor with no CSS must be functional. The vanilla path renders no table chrome, so a host that renders its own cells and calls `attachElement` owes the declaration on them. The library offers no override point for it, which is deliberate and matches RI1; that is weaker than saying CSS cannot reach it, because an author `!important` rule still wins, and the case that needs one is real — a code block renders through the same inline host and may want `white-space: pre` with horizontal scroll. `pre-wrap` honors an interior newline but gives a trailing one no line box, so a field whose logical text ends with `\n` also gets a trailing `<br>` (`trailingLineBreak.ts`), maintained by both reconcile paths: appended into the fragment by `fullReconcileDeltasToDOM`, and cleared before the child walk in `applyDeltaToDOM` then re-synced after, because an insert landing on the break finds a `<br>` with no text leaf and bails to a full reconcile — which would be every keystroke at the end of such a field. It is marked (`data-pen-trailing-break`) so the reconcilers can find it, and being a childless element it contributes no logical length and no logical text, so the `inlineAtomLogicalDom.ts` offset mapping, the FE7 selection bridge, and the `extractTextFromDOM` watchdog all read through it and it never becomes document content. It does carry a line box, so `collectLineFragments` emits a zero-width fragment for it on the same branch as the placeholder: a line no text lands in is still a line G5 vertical motion has to stop on. The end position then resolves by affinity, downstream onto the trailing line and upstream to the end of the line above.

- RI6. A container is declared by its schema, never by a type list inside a renderer: `isContainerBlock` (`@input/pen-core`) treats nested `content` or an explicit `isContainer: true` as containment, and `isContainerBlockType` (`@input/pen-core`) resolves it for a block type. `blockquote`, `callout`, and `toggle` carry the flag because they are the built-ins, not because they are special — previously each of the three renderers plus the DOM document tree hardcoded that same set, so a host-defined container could hold children that no surface ever rendered, which is silent content loss rather than a missing feature. Two nesting routes are both authoritative and a container may mix them: a block's `children` array, whose children are deliberately absent from `blockOrder`, and the `parentId` prop, whose children sit in `blockOrder` as siblings. `documentState.childrenOf` is the only supported lookup and is the inverse of `parentOf`, returning children-array order first and `parentId` children in `blockOrder` sequence; filtering `blockOrder` on `parentId` is the mistake that route invites, because it cannot see children-array children at all. Each rendering surface exposes exactly one children outlet — `Pen.Editor.BlockChildren` in React, `ctx.childNodes` in Vue, and a children host element created by `documentTree` for the vanilla path — while headless has no outlet and only resolves children. Collapse stays the renderer's decision through `shouldRenderContainerChildren`, which reads resolved rather than stored props (`open !== false`) so a container whose `open` defaults to `false` stays collapsed when normalization has stripped that default from storage, which is exactly `toggle`'s shape; DOM navigation calls the same predicate, so keyboard traversal and rendering cannot disagree about what is visible. One gap stays stated rather than fixed: a `parentId` naming a non-container renders nowhere, since `getRootBlockIds` drops every block with a parent and a non-container is given no children host. Evidence is per surface, as HB5 requires — `packages/rendering/react/src/__tests__/customContainerRendering.test.tsx`, `packages/rendering/vue/src/__tests__/customContainerRendering.test.ts`, `packages/rendering/dom/src/__tests__/customContainerRendering.test.ts`, and `packages/core/src/__tests__/containerChildren.test.ts` for the headless model.

- RI7. Mark wrappers expose every stored prop a host must recover from the live DOM. Built-in semantic marks use HTML elements (`strong`, `em`, `u`, `s`, `code`, `a`, `mark`). `link` writes `href` and `title`. `suggestion` writes `data-mark-type`, `data-suggestion-id`, `data-suggestion-action`, and the review-surface class. The three colour marks share one path: each writes `data-color` — the stored `color` string, whether a CSS colour or an opaque host token — and paints through a `var()` fallback, so `highlight` is `background-color: var(--pen-highlight-color, <value>)` on `<mark>` while `textColor` is `color: var(--pen-text-color, <value>)` and `backgroundColor` is `background-color: var(--pen-background-color, <value>)` on a `<span data-mark-type="…">`. `<mark>` carries no `data-mark-type`, because a semantic element is its own type; hosts select `mark[data-color="…"]`. The library never assigns those custom properties, so a host stylesheet that sets one on the mark wins at normal specificity and needs no `!important`. The corollary is that the paint is an inline style: a host rule setting `color` or `background-color` on the mark itself no longer applies, and setting the token is the only supported remap. A colour mark whose `color` prop is missing, non-string, or empty paints nothing and writes no `data-color`. Unknown marks fall through to `<span data-mark-type="…">` with no props copied. Export serializers (`serialize.toHTML`) are a separate surface and are unchanged by this rule — they still interpolate the stored value into an inline `style` on the exported HTML, which is also why copy carries the stored colour rather than the `var()` string: clipboard HTML comes from `schema.serialize.toHTML`, never from the live DOM.

## Retired

No member of SCH, FE, G, OV, DIR, BR, M, or RI is retired. FE9 was added after a host `editor.apply` remapped the authority caret but left EditContext and `edit-context-textupdate` on the pre-apply offset, so the next keystroke clamped or inserted in the wrong place. FE10 was added after a drag from the content padding beside the column selected nothing at all: `mousedown` outside a block opened no gesture, so the two handlers that grow a selection had none to grow and the model's collapsed caret was what survived the gesture. RI5 was added after Shift+Enter shipped storing a `\n` that nothing rendered. RI6 was added after a host-defined container proved unrenderable on every surface despite a working data model. RI7 was added after `textColor` and `backgroundColor` fell through to the unknown-mark span and dropped the stored colour, so on-screen paint and host restyling had nothing to select; `highlight` was folded into the same path in the same change rather than left on its older direct-inline-style taste, which would have kept one of the three colour marks unremappable without `!important`. The geometry rules no longer depend on a storage sentinel: the `\u200B` empty-block sentinel that G1's original wording measured through is gone from storage, so offsets resolve through `offsetDomain.ts` alone and no measurement path tests for a sentinel.
