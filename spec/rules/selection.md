# Selection Rules

These rules govern selection end to end: the authority that owns selection truth, the normal-position policy, how DOM-originated proposals are read, when the authority is projected back into the DOM, overlay caret rendering, selection type transitions, IME containment, and the standing invariants. The authority lives in `@input/pen-core` (`packages/core/src/editor/selection.ts`), the normal-position and transition functions in `packages/core/src/selection/`, and the reader, projector, and input backends in `@input/pen-dom` (`packages/rendering/dom/src/field-editor/`). The library owns selection: the DOM is a sensor (pointer, IME) and a display (native caret inside the active field, overlays everywhere else). No component infers selection truth from the DOM outside the reading rules below, and no component writes the DOM selection outside the projector.

The rules here are the contract for selection bridging inside `@input/pen-dom`: one reader (`selectionReader.ts`) and one writer (`selectionProjector.ts`) implement them, and conformance and the seeded DOM fuzzer check them in real browsers. Treat a divergence as a defect against these rules, not as a second contract.

The letter `R` names two unrelated families. `R1`–`R3` in this document are reader gesture-window admissibility rules. `R1`–`R8` in `spec/rules/facets.md` are facet provider and combine rules. Neither family was renamed.

## A — Selection authority writes

The authority holds exactly one `SelectionRecord` (`state`, `version`, `origin`, `commitId`). There is no pending/committed/programmatic triplication; concurrency is resolved by version comparison at the consumers. `set(state, { origin })` is the only write entry point, and `onCommit` is registered by the commit pipeline and is not callable by extensions.

- A1. Validation is total: every point's block must exist and every offset is clamped to that block's logical length, and a text selection validates both the anchor block and the focus block. An invalid block reference rejects the write and emits a `diagnostic` event; it never throws and never partially applies. A cell selection's `text` is accepted only when `anchor` equals `head`, and its offsets clamp to that cell's logical length.
- A2. Deep-equal states coalesce: the version does not increase and no event fires. Equality is type-specific — text includes `affinity` and excludes `goalX`; block includes `blockIds` and `head`, where a missing `head` defaults to the last `blockIds` entry and otherwise the first; app is `appId`; cell includes `blockId`, `anchor`, `head`, and `text`, the in-cell range of a cell being edited. The reader's echo filter uses this same relation for block, app, and cell proposals.
- A3. Every `selectionChange` emission carries the new record, never a bare state and never a bare `null`, and `set` emits synchronously after the record is swapped so re-entrant `set` calls from listeners apply in order and each produces its own version. The document-swap reset of A6 emits a record whose state is `null`, and a repaired write emits after `commit` listeners rather than from inside `onCommit`.
- A4. `origin: "gc"` is reserved for the authority's own repair writes and is never accepted from callers.
- A5. On commit the authority repairs its endpoints as anchors rather than mapping them through the commit summary (see AS1–AS5 in `spec/rules/anchors.md`): if the repaired state is identical the record is untouched, so the version is stable across commits and renderers may rely on that; otherwise the repaired state is written with `origin: "mapped"` and the commit's id. The surviving observational guarantees are pinned: a non-collapsed text selection associates its anchor upstream and its focus downstream while a collapsed caret associates downstream on both, a block selection drops deleted ids and falls back to a collapsed text position at the first deleted block and then to `null`, and a cell selection clamps row and column into the post-commit grid while a table structure change resets it to a collapsed text selection in the table's first cell (`{ anchor: (0,0), head: (0,0), text: { anchor: 0, focus: 0 } }`). A structure change is one that summarizes as `table-changed`: rows or columns inserted, removed, moved, merged, or split. A props or meta change on the table summarizes as `block-props-changed` and leaves an edited cell, including its `text`, where it was.
- A6. `updateDocument` (document swap) is the only full reset: the record becomes state `null`, version incremented by one, origin `"programmatic"`.

## N — Normal position policy

Not every `{ blockId, offset }` pair is a caret position. `nextNormalPosition` and `snapToNormalPosition` live in `packages/core/src/selection/normalPosition.ts` and are not interchangeable. The reader's echo filter and accept-path placement call `snapToNormalPosition`; caret commands and the fuzzer call `nextNormalPosition`. Arrow keys next to an inline atom are outside the pair: they dispatch through the keymap like every other caret key, so M2's swap applies, and treat the atom as an object (`stepInlineAtom` in `packages/core/src/commands/caretMotion.ts`), selecting the atom on the side of travel — between two adjacent atoms, each direction selects its own neighbour — instead of snapping to a side. A shift-extend moves the focus over the atom in the direction of travel. No renderer intercepts these keys before the keymap, and the write carries origin `keyboard`.

- N1. In text-capable blocks (`usesInlineTextSelection`) every logical offset from `0` to the block length is normal, except offsets strictly inside an atomic inline node. An inline embed occupies one logical offset, both of its sides are normal positions, and its interior does not exist in the logical domain.
- N2. Non-text blocks such as images, dividers, and apps-as-blocks have no text positions and are selected as `BlockSelection`. A text write that covers the whole `0..1` span of a single non-text block is escalated to `BlockSelection` at the authority; a collapsed caret on a table and a mixed-boundary range with one endpoint mid-paragraph still admit the `0..1` clamp, because escalating the former disables table autocomplete and escalating the latter would turn a suffix-plus-divider delete into a whole-paragraph delete.
- N3. There are no between-block text positions. The gap between blocks is represented by `BlockSelection`, never by a text selection with a synthetic offset.
- N4. `nextNormalPosition(doc, point, dir)` is the single definition of where the caret may step: within a block it advances one grapheme cluster (`Intl.Segmenter` in locale-independent mode), and at offset `0` or the block length it yields a block-boundary marker so caret commands decide whether to enter the neighbouring text block, select a non-text block, or stop at the document edge. It always advances by a grapheme or yields a boundary, so it is never the echo-equivalence test.
- N5. `snapToNormalPosition(doc, point, dir)` is the non-stepping companion: an already-normal point is returned unchanged and `dir` is ignored, a point strictly inside an atom snaps to that atom's end when `dir` is forward and its start when `dir` is backward without stepping past it, a point on a non-text block yields a block boundary, and a missing block yields `null`. Offsets outside `0..length` clamp onto the block before those tests are applied.
- N6. Lookbehind and query matching that consume caret offsets — `resolveSuggestionMenuTarget` and `useSuggestionMenu` — read the same logical domain as `block.length()` and the caret: each inline atom occupies one offset. They must not slice `block.textContent()` with those offsets, because stored string text omits atoms (IOP7). `inlineLogicalText(block)` is that domain as a string (U+FFFC at each atom). A match whose query range contains an atom is not a text trigger. An `@` (or other trigger) immediately after an atom resolves at the offset after the atom; `boundary: "whitespace"` still rejects when the preceding unit is the atom rather than whitespace. Under `boundary: "whitespace"` the match anchors on the last trigger preceded by whitespace or sitting at the start of the lookbehind, so a later trigger character with no whitespace before it is part of the query (`@ada@example` is one query).

## R — Reader gesture windows

The reader (`packages/rendering/dom/src/field-editor/selectionReader.ts`) owns the only `selectionchange` listener: one per editor root, bound when the field editor gets its root element whether or not a field is attached. Backends do not listen; they report gesture inputs, and the root itself senses `pointerdown` and `contextmenu`. No backend pre-filters or restores a read: an echo of the record stops at step 3, and a non-equivalent read is decided like any other (accepted in a window, otherwise projected back by P2). When the DOM already shows the record and only an EditContext buffer lags, the projector writes the buffer and leaves the native range alone. Input handlers do not map the live selection: a keystroke or `beforeinput` edits the authority, after asking the reader to read the live selection first when a gesture window is open (with every window closed a read cannot change the authority, step 4). Two inputs still read their field until the authority can hold their caret: an active table cell, and a field activated with no caret in the authority, where the browser's caret is the only one. Document shortcuts ask the reader whether the live selection is inside the root. Renderer chrome — the selection toolbar, the contextual AI prompt, the slash and suggestion menus — positions itself from the authority through the geometry reader and observes `editor.onSelectionChange`, never the live range or `selectionchange`. DOM-originated selection changes are proposals, and a proposal is accepted only inside a gesture window. There are four windows, named by the reader's own gesture-event kinds rather than by native event names: pointer opens on `pointerdown` and closes on `pointer-settled`; ime opens on `compositionstart` and closes on `compositionend-completed`; context-menu opens on `contextmenu` and closes on the next `selectionchange` after it, whatever that read decides — an echo of the record (step 3) or a range outside the root closes it too; drag opens on `dragstart` and closes on `drop-completed` or `dragend-completed`. Keyboard is not a window: every selection-affecting key is a command that writes the authority directly, and the browser's default caret motion is always prevented, so no keyboard-originated `selectionchange` should occur. The one exception is an active IME composition, where key events are not intercepted (see C1).

- R1. The close inputs `pointer-settled`, `compositionend-completed`, `drop-completed`, and `dragend-completed` are specified gesture inputs, not native events; a backend or host maps native events onto these names and does not invent synonyms. `pointerup` is a recognized input that leaves window state unchanged, and the observer that saw it schedules `pointer-settled` one microtask later so a click-collapse settles first; that microtask is the single deferral S4 admits, and the S4 lint matches it by shape (a callback in the reader that advances the windows with `pointer-settled` and calls no setter), not by waiver. The reader's own document `pointerup` listener first reads the live selection while the pointer window is still open: a drag's last range and a multi-click's word or paragraph expansion, which engines apply on press, are in the DOM by then, but their `selectionchange` is queued behind `pointer-settled`. Multi-click is read this way and only this way, with no frame wait, and mouseup writes only what Pen computes. A document `pointercancel` maps onto `pointerup` through the same listener, because no `pointerup` follows it: a touch pan the engine took over, or a native drag that starts while the pointer window is open, ends the pointer gesture there, so a later `selectionchange` is not admitted as `pointer` (I4, S3). The listener exists only between a press and the event that ends it, and detaching the root releases it. Windows are root-level reader state: a field deactivation or session switch — including the one a press in another block causes in the gesture that opened the window — leaves every window as it is, except that a field torn down mid-composition emits `compositionend-completed` for the composition it owned. Only the close inputs above and the root's detach close a window. `keydown` and `keyup` are recognized and are no-ops on window state, so a sensor can feed the same function without a special case. A backend that cancels `dragstart` — every Pen backend, since Pen has no drag-move for text — emits `dragend-completed` in the same handler, because a cancelled `dragstart` is followed by neither `drop` nor `dragend`; a document-level `dragend` maps to `dragend-completed` for any drag that is not cancelled. The `native-range` window covers touch selection handles, which move the native range with no pointer window open. It opens when a long-press, `selectstart`, or `contextmenu` from a coarse pointer — the root's latest `pointerdown` was `touch` or `pen` — establishes a non-collapsed native range inside the active field (one block's text, or the edited cell's `CellSelection.text`); that read is accepted. It closes on the next `pointerdown` inside the editor content, on the read that collapses the native range (decided inside the window), or when an authority write that the reader did not make supersedes the record; a `mapped` write carries the reader's record through an edit and does not supersede it. A collapsed read while the long-press is still waiting for its range drops it, because engines also send `selectstart` for a tap that places a caret. While it is open, proposals are accepted with origin `pointer` and the projector does not replace the range with an S2 exception state. It is state-based: no timer, counter, or microtask opens or closes it (S4).
- R2. `pointerdown` and `dragstart` as gesture inputs already mean "in editor content" and carry no inside-content flag, so the observer of the native event must not emit them for a target outside editor content, including overlays and widgets. Forwarding an outside `pointerdown` is a sensor bug: it opens a window and admits a later browser-quirk `selectionchange`. `pointerup`, `drop`, and `dragend` are not in-content gated and may fire outside the content after an in-content start, which is why the pointer window does not close on `pointerup` of the field element alone.
- R3. Windows are independent flags, two or more may be open at once, and opening one never closes another; a `selectionchange` is admissible if any window is open. This is load-bearing for click-during-IME: `pointerdown` must still open the pointer window so the click's `selectionchange` stays admissible after the ime window closes. A composition overlapping a pointer drag keeps both windows open and the reader does not cancel the composition, which C3 owns.

On `selectionchange` the reader runs one algorithm:

1. (Retired.) There is no in-flight projection to ignore: projection is synchronous, so no `selectionchange` lands inside one, and the projector verifies its own write by reading it back.
2. Map the DOM selection to a logical proposal. An unresolvable DOM selection — outside content, inside an overlay or a widget — produces no proposal.
3. Apply the snap rule: if the proposal is logically equivalent to the current record state, stop. Equivalence is type-specific and different types are never equivalent. Text endpoints are compared after `snapToNormalPosition` on the same snapshot; the two sides of an atom are distinct normal positions and are not equivalent, while a proposal point strictly inside an atom is equivalent to either normal side of that same atom, because a browser interior offset is not a user move between the sides. `affinity` and `goalX` are not DOM-readable and are not part of echo. Block, app, and cell proposals use the A2 relation, so the same `blockIds` with a different `head` is a real change of extend direction (T4) and is not swallowed. A single-field native range while the authority spans blocks is refused rather than accepted, on both the accept path and the diverge path, unless the proposal is collapsed — a click inside a multi-block selection is real new intent.
4. If no gesture window is open, the DOM has diverged without user intent. Do not write the authority; request re-projection in the next flush (P2).
5. If any gesture window is open, normalize the proposal — clamp offsets, then `snapToNormalPosition` on each point with `dir` toward the gesture's focus, defaulting to forward when the gesture has no direction — and write it. The origin is `ime` whenever the ime window is open and `pointer` otherwise, covering the pointer, drag, and context-menu windows; there is no `drag` or `context-menu` origin. A pointer proposal spanning multiple text blocks produces a multi-block `TextSelection`.

Reads are never escalated by block type or by block count, in any document profile (T2, T3, N2): a pointer range covering a divider or a table and a text block stays a `TextSelection`. Writes escalate, reads do not. The reader never calls `preventDefault`, never mutates the DOM, and never dispatches commands.

## P — Projection triggers

Projection runs inside the DOM scheduler's write phase and has exactly two triggers.

- P1. Projection runs in the flush following any `selectionChange` whose record version is newer than the last projected version.
- P2. Projection also runs in the flush following a reader divergence report, even though the record version is unchanged.
- P3. Projection runs in the same turn as a DOM rebuild of a mounted projection target (a field reconcile or a decoration rebuild), after the rebuild. Reconciles never save and restore the native range themselves: the code that rebuilt the element asks the field editor to project, and the request is a no-op unless a rebuilt block is the projection target.

There are no other triggers, and no retry loop. Projection requires the target block's element, which renderers supply through the mount-ack protocol (`ackBlockMounted(blockId, element)` once commit-driven DOM updates for that block are in the DOM). If the element is present the projector writes synchronously and then verifies by reading the DOM selection back; a read-back that does not map to a state logically equivalent to the record, or that leaves focus off the projection target, emits `diagnostic { code: "selection-projection-mismatch" }` with the record version, the trigger, both values and the surface, once per version and trigger, and is never silently retried. If the element is absent the projection parks on `(record.version, blockId)`.

- P4. A renderer acks every block element it mounts or replaces, in the turn of the DOM commit that mounted it, and an ack for the parked block projects the record in that turn while the parked version is still current; an ack for any other block is a no-op.

A renderer that moves a mounted block element instead of replacing it (the vanilla tree moves a block into another AX1 list group wrapper) drops any focus held in it, as every DOM move of a focused node does; it acks that move in the same turn (`ackBlockMoved(element)`), and the field editor restores focus to the element that held it, through the focus controller, and projects the record into it. That focus was the editor's, so the restore is not withheld under HOST9. A parked projection is discarded when a newer version parks or projects, and the scheduler neither retains nor retries a parked record. On park the projector asks the host's mount requester, if one is installed, to mount the block in the same turn, and queues one check for the write phase of the flush after the park: if the projection is still parked on the same version and block, it emits `diagnostic { code: "selection-target-unmounted" }` with `version`, `blockId` and `mountRequested`, once per park, and keeps the park. An unmounted selection target is either about to mount under virtualization or a renderer bug that must surface. A gesture window governs DOM-originated proposals only: an authority write is not a proposal, and S1 and S2 require the projector to write it out regardless of gesture state. Every authority-driven projection (P1, P2, P3, or a parked mount-ack) is withheld under HOST9: while a native text-entry control that is not this editor's field (outside the root or nested in it) or another editor owns focus, and while focus is anywhere else outside the root unless the record is an unprojected write whose origin takes focus (`pointer`, `keyboard`, `ime`, `restore`, or `mapped` by a local `user`-origin commit), the record is kept and not written, because a DOM selection written into a field moves focus with it; the next trigger that finds focus in the editor projects it. P2 and P3 are also withheld while focus is on editor chrome inside the root — a block handle, a detached menu item, a toolbar button: anything focused in the root other than the root itself, the focus sink, or a field surface — because the write would take focus from the control AX3 returned it to (a reorder that moves the active field's block can leave a divergent native range behind; Firefox reports it). Gesture and programmatic projections are not withheld. While the IME window is open the composing field owns its DOM range (C1, C2), so authority-driven projections are withheld there too and `compositionend-completed` releases one projection of the record (trigger `window-closed`). A projection that finds the DOM already equivalent to the record, focus on its target, and the backend's own selection state (an EditContext buffer) matching writes nothing. P2 does not re-project a version whose last projection reported a mismatch while the divergent read equals that reported read-back: the engine normalized the write, and writing again would loop. Scroll-into-view is a projection option — `"auto"`, `"none"`, or `{ align }` — measured in a scheduler read phase and applied in the following write phase, keyed by record version and skipped once a newer version has projected. `"auto"` scrolls the target to the nearest edge for records with origin `keyboard`, `ime`, or `restore` (undo and redo bring the restored selection into view) and for `mapped` records produced by a local `user`-origin commit, and does not scroll for `pointer`, `programmatic`, `gc`, or a record mapped through another peer's, the AI's, or a history commit, so a collaborator's typing never moves the local viewport. `scrollIntoView` brings a block or the selection into view through the same read and write.

Focus is a projection concern, and `field-editor/focusController.ts` is the only `@input/pen-dom` module that calls `HTMLElement.focus` (`pen/no-direct-dom-focus`, with no allowlist). The editor root owns a hidden, permanently focusable sink element. DOM focus sits on the active field element during text editing; on the revealed sink for a block or cell selection; and on the editor root for an app or `null` selection, never on the sink, which AX1 keeps `aria-hidden` there. The root is focused only while the editor already owns focus, so a `null` selection on mount or load never pulls focus into an editor the user did not focus. Escape and a field deactivation focus nothing themselves: Escape writes the record (origin `keyboard`) and a deactivation leaves it, and the projection of that record places focus. No path focuses a block element. The root transfers focus into the active surface only when focus enters it from outside the editor (Tab, a host's `focus()`): a single-block text record focuses its field, a multi-block text range within the block-surface threshold is projected as an activation into the expanded host (S2), and a block, cell or substitute record focuses the sink; focus that reaches the root from inside the editor is a projection and stays there.

## O — Overlay caret and selection rendering

The native caret and native selection remain the display inside the single active text field, because browsers are reliable there and IME depends on it. The overlay layer, drawn from geometry-reader rects measured in read phases, is the display everywhere else. O1–O5 are the mandatory list, not the exhaustive one: each names a case where the browser gets the caret wrong and Pen must override it. The overlay is built once in `@input/pen-dom` and drawn into the root's overlay layer (OV2) on every surface; React, Vue, and the vanilla mount bind to it rather than draw their own. A host may additionally opt into the overlay for all collapsed editing through `customCaret` (default off), which in React mounts `Pen.Editor.CaretOverlay`; that is a mode O1 does not govern, not a divergence from it. Both modes owe the same guarantees: no overlay caret while composing, so IME always sees the native caret; none while the field lacks focus or the renderer is read-only (O5), where focus also requires an active window — switching windows leaves `document.activeElement` inside the root, so the vanilla mount and both bindings track root focus through pen-dom's `bindEditorRootFocus`, which reports current focus once on bind without replaying focus entry, then follows the window's `blur` and `focus` as well as the root's `focusin` and `focusout`; and a solid caret under `prefers-reduced-motion` (AX6) whatever the host's animation token says. The local caret restarts its blink phase whenever a commit has a `user` origin or a `pointer`, `keyboard`, or `ime` write moves the caret; the restart replaces the caret element in the scheduler's write phase, so a CSS animation starts again at its first frame without a timer or a read, and the caret stays solid while the user types. The cycle comes from the host through `--pen-editor-caret-animation`. The overlay never measures; all rects come from the geometry reader in read phases.

- O1. A collapsed selection adjacent to an atomic inline node, on either side, is drawn by the overlay at the geometry rect for that point and affinity, because browsers misplace or hide the caret next to embeds.
- O2. In an empty text block (logical length 0) the caret is drawn at the `<br data-pen-empty="">` placeholder line box that `@input/pen-dom` renders in the write phase.
- O3. Block and grid-cell selections render as overlay outlines in the root's layer, with no native caret anywhere: one outline per block up to fifty selected blocks, one outline per contiguous run above that, and one outline around the anchor-to-head cell rectangle while no cell is being edited. Outlines follow the selection in read-only editors too. `data-selected` stays on block hosts as a styling hook and is not the O3 rendering. App selections are not outlined, because no surface maps an app id to an element.
- O4. Multi-block text selections keep the native selection visible and add an overlay endpoint caret at each endpoint that meets an O1 or O2 condition. Endpoint carets do not blink and never hide the native caret. Where S2 declares that a text range is not written natively, the overlay draws both endpoint carets, the partial spans in the endpoint blocks, and one span across the fully covered blocks.
- O5. Read-only editors never show the overlay caret; the native selection stays allowed so content can be copied.

When the overlay caret replaces the native one under O1 or O2, or everywhere under `customCaret`, the native caret is hidden with inline `caret-color: transparent` on the active field, written in the same write phase as the paint and restored when the overlay caret goes, including the moment composition starts.

## T — Selection type transitions

One deterministic state machine (`packages/core/src/selection/transitions.ts`) of pure functions, consumed by commands, by the reader, and by the pointer path. Drags form through T2's `convertPointerDrag` and block clicks through T5's `clickSelectableBlock`, both via pen-dom's `resolvePointerSelectionIntent` over a `buildTransitionSnapshot` scoped to the blocks they touch; pen-dom keeps no transition logic of its own, and its text/structural split is core's, so a code block is text for the pointer exactly as for the authority. Every exported transition has a production consumer.

- T1. Select-all walks an escalation ladder — field text selection, whole-block text selection, the enclosing container's blocks (list, layout cell, table block set), then all top-level blocks as a `BlockSelection` — one rung per press, with the rung computed from the current state and never from a counter. The ladder has two entry rungs chosen by the host's interaction model and threaded through `editor.selectAll(behavior?)`: `"block-first"` enters at the whole-block rung, and the default `"content-first"` enters at a content rung whose single press is a `TextSelection` from the first block at offset 0 to the end of the last block in document order, where a structural last block contributes its `0..1` unit extent (N2). The content rung is taken only when the current selection is text-or-empty and does not already cover that range, so a second press escalates instead of sticking, a block, cell, or app selection never walks backwards into it, and a document of entirely empty blocks starts at `BlockSelection` rather than a collapsed caret. A multi-block `TextSelection` from select-all keeps the field editor's expanded surface and does not deactivate it.
- T2. A pointer crossing a text-block boundary while dragging converts a collapsed or single-block text selection into a multi-block text selection, and dragging across a non-text block includes it as covered content while the selection stays a text selection. Document profile does not modulate this: a pointer range covering a table or any other non-text block plus a text block stays a `TextSelection` in both flow and structured documents. A text endpoint on a table block covers the table as a structural unit rather than placing a caret in a cell, and starting inside a cell and then leaving the grid collapses the origin to the table block at offset 0, because cell text is addressed by row and column and a mid-cell offset has no meaning outside the grid.
- T3. A text selection that covers every offset of two or more blocks with both endpoints at block edges escalates to `BlockSelection` only on select-all rung 2 or higher — never implicitly during a pointer drag or shift-click, and never at a block-count threshold. A block-count heuristic may choose a field-editor surface mode, but it must not write `BlockSelection`.
- T4. From a `BlockSelection`, `ArrowDown` and `ArrowRight` collapse to a caret at the start of the block after `head`, or the end of `head` when it is last; `ArrowUp` and `ArrowLeft` collapse to the end of the block before `head`, or the start of `head` when it is first. `Shift+Arrow` grows or shrinks `blockIds` at `head`.
- T5. Clicking a selectable non-text block sets a `BlockSelection` with that block as `head`; clicking a text block sets a collapsed text selection at the pointer's normal position. A shift-click in a text block other than the anchor's extends the selection from the anchor to that same point — the logical offset under the pointer, with an inline atom's side taken from the half the click lands on, read in the direction of the bidi run the atom sits in (BR2), not the block's, so the visual left half is the atom's start in a left-to-right run and its end in a right-to-left run (O1) — not to the clicked block's edge, on every binding. A shift-click on a block with no text position of its own (a divider, an image), with the anchor in another block, extends the same way, its focus that block's far edge in the direction of travel (N2), on every binding. Keyboard vertical motion (G5) that measures a point on a non-text block writes the same `BlockSelection`, matching `crossBlock`; one that measures a point on a table enters it as a `CellSelection` on its edge cell — the first row moving down, the last moving up, column 0 — as a click on a cell does, because a text point on the table block has no field to project into and left focus nowhere (S2); with Shift held it extends over the table as a block. Escalation drops `goalX` because a block selection has no column.
- T6. Cell selections arise only inside table blocks, through a pointer drag across cell boundaries or `Shift+Arrow` from an active cell. Leaving the grid with an arrow at a grid edge produces a text or block selection with T4 semantics relative to the table block, and in-cell caret motion stays a `CellSelection` whose `text` carries the caret, because a text point on the table block is the wrong offset domain.
- T7. A plain `ArrowLeft`/`ArrowRight` on a non-collapsed `TextSelection` collapses it to the document-order start or end of the range and moves nothing further; `Shift+Arrow` extends as usual. K1 prevents the browser default for every navigation key, so this collapse is Pen's to perform: stepping the focus instead would leave a select-all whose focus sits at the document end (T1) standing, with the next keystroke replacing the whole document. A range that exactly covers one inline atom collapses to the same edges (N1).

## C — IME and composition

- C1. During composition the ime gesture window is open, the reader accepts composition-driven selection updates, and caret commands and keymap dispatch are disabled except `Escape`, which never calls `preventDefault` during composition. On the EditContext backend the session opens on `compositionstart`, which Chromium fires on the EditContext itself (not on the element) before a composition's first `textupdate`; an element `compositionstart` opens it too. A `textformatupdate` opens it only when it directly follows a `textupdate` applied with no composition open: that update was the composition's first, and is rewound into it (C4). A `textformatupdate` with nothing to rewind opens nothing, and its `getTextFormats()` list is commonly empty. On the contenteditable backend a composition that ends without changing the field — cancelled, or committed empty — returns the authority to its state at `compositionstart` (mapped through any deferred deltas, C2): the carets the reader accepted inside the composed run do not outlive it, so the next keystroke lands where the composition began. A composition in the expanded host (FE2) opens and closes the ime window like a field's, so authority-driven projections are withheld while it runs; its caret sits at the range start in text the record does not hold, so a read while the expanded host composes is not accepted — it diverges, and that projection is withheld with the rest until `compositionend-completed` releases one — and the cross-block record and the expanded surface stay until the commit replaces the range.
- C2. An edit the composition did not produce, arriving mid-composition — a collaborator's, the AI's, an extension's or a programmatic one, whatever its origin — does not touch the composed field's DOM: the composition start point and the authority record are repaired with `origin: "mapped"`, and its deltas are deferred until `compositionend`. On the contenteditable backend that is every delta while composing, because the composition writes nothing to `Y.Text` before `compositionend`. The outcome is defined against two `Y.Doc`s: the result equals what a local doc applying the IME's edit and a remote doc applying the other edits produce once they exchange updates, with the remote edit ordered first where the two insert at one point. On the contenteditable backend Pen chooses the position: at `compositionstart` it records the field's logical text (one U+FFFC per inline atom, the `Y.Text` index space) and the start of the authority selection; after `compositionend` it takes, among the minimal diffs from that text to the field text, the one nearest the recorded start (a fresh composition at a caret and a reconversion of a selection are exact; recomposing a word that borders a run of repeated characters can be explained by a different minimal diff, which is the documented residual); and it rebases that diff over the deferred deltas by replaying the base text through them with Yjs's placement — the composed text goes immediately before the original character that followed the replaced range, so a remote insert at the composition start or inside the replaced range lands before it, and only the replaced range's surviving original characters are deleted, so a remote insert inside it survives — then applies the result as one `user` apply and projects the caret to the end of the composed text. On the EditContext backend the composed text stays out of `Y.Text` while the IME runs (C4), and every `Y.Text` change in the meantime — a collaborator's, a host or AI apply, history — is deferred from the composing field's buffer and DOM; the one commit takes the replaced range of the text at `compositionstart` to the composed text and rebases that edit over the deferred deltas with the same Yjs placement as the contenteditable rebase, so a remote insert inside the replaced range survives, then puts the caret after the composed text, syncs the buffer with one `updateText` over the changed span, and rebuilds the field once. A property suite pins the contenteditable rebase against the two-`Y.Doc` oracle at 300 cases per pull request and 20,000 nightly.
- C3. `compositionend` ordering quirks are contained in the backend: reconciliation runs once the backend has observed DOM quiescence for the composed field within the same task-queue turn, and its result enters the pipeline as an ordinary apply. No `setTimeout`-based composition timers are permitted. Quiescence is decided from the composition event sequence itself — reconcile this turn when the live DOM already differs from the recorded start text or the `compositionend` data is already in the field, otherwise let the following mutation complete the sequence, and flush leftover text when a second `compositionstart` arrives first.
- C4. The EditContext backend remains preferred and its composition ranges feed the same reader and authority path. A `textupdate` with no composition open applies immediately at origin `"user"`, because that path is load-bearing for undo, suggestion refresh, and autocomplete. A composition has one lifecycle: it opens per C1, stays open across every `textupdate`, and closes once. While it is open each `textupdate` range is read in buffer coordinates against the composition — an update that reaches past the composed text grows the range it replaces — and the composed text is painted into the field DOM in place rather than applied, so the native caret and the selection record stay on the replaced `Y.Text` range and never point into text `Y.Text` does not hold; `keydown` runs no command, keymap, or reader catch-up, and the backend's own handlers write neither the buffer nor its selection. A non-empty `compositionend` commits the composed text once, as one `"user"` apply over the replaced range (rebased per C2), with the caret after it; an empty `compositionend` or `Escape` drops it; deactivation (a blur, a click elsewhere) commits it without moving the selection, as Chromium keeps the text. The buffer then takes `Y.Text` once and the field is rebuilt from it. Outside a composition the buffer follows `Y.Text` by diff, so an edit the IME already made is never replayed into it. When a composition opens from its first update's `textformatupdate` (C1), that update's apply is rewound at origin `"system"`; relabelling ordinary typing as `"system"` would make it un-undoable, and rewinding as `"user"` would re-insert discarded text on the first undo.

## S — Selection invariants

- S1. At most one component writes the DOM selection (the projector, `selectionProjector.ts`) and one component reads it (the reader, `selectionReader.ts`), and both live in `@input/pen-dom`. Writing is any `Selection` mutator and `EditContext.updateSelection`. The `pen/no-dom-selection-write` lint rule enforces the writer half over the production sources of `@input/pen-dom`, `@input/pen-react`, and `@input/pen-vue`, with no allowlist. Reading is `getSelection()` on a document or window, a `selectionchange` listener, and the live-selection mappers; `pen/no-dom-selection-read` enforces the reader half over the same scope, with no allowlist. Backends that need the live range inside their field (the caret the browser left after its own edit, before the diff reaches the model) ask the reader directly (`SelectionReader.fieldOffsets`, the field editor's internal `reader`), and the projector takes the `Selection` it writes through from the reader's `nativeSelectionForWrite`, which the lint flags anywhere else. A block or null selection is projected by clearing any native range inside the root, and `focus()` without a caret in its field commits one to the authority and projects it rather than placing a native caret of its own.
- S2. After every flush with editor focus, the DOM agrees with `authority.record.state`. A text selection is a native range in its field or the expanded host that maps to a logically equivalent state (reader step 3), with focus on that field or host; a block or cell selection has no native range inside the editor root and focus on the sink revealed with the matching role; an app or `null` selection has no native range inside the editor root. The composing field is exempt while the ime window is open, because composition owns it (C1–C4). Two text states are declared exceptions with a pinned substitute: a text selection whose block range spans more than 50 blocks (`block-surface-range`, the block surface mode; `BLOCK_SURFACE_MODE_THRESHOLD`), and a multi-block text selection whose projected range the engine confines to a single field (`engine-confined-range`, the read-back is `isSingleFieldNativeLeftover`). Their substitute is no native range inside the editor root, focus on the sink revealed as a text range (`role="group"`, labeled `pen.a11y.textRangeSelected`), and the overlay painting both endpoint carets plus the range items (a partial `range` in each endpoint block and one `block-span` over the covered blocks; O3, O4); conformance asserts the substitute so the exception cannot widen into a hole. The projector writes the substitute directly for the first and falls back to it once, without a mismatch diagnostic, when the read-back of the second shows the confined range; a later projection of that version writes the substitute, not the range again. While the pointer window is open a native range equivalent to the record also satisfies this rule, and the substitute is applied once by the pointerup projection (`window-closed`). The projector exposes the state as `getSubstituteState()` (forwarded by `FieldEditorImpl`), a pure read of the record and projector state that the overlay calls in its read phase. While a substitute holds, the sink routes input: `keydown` runs the text keymap against the authority (a printable key with no modifier replaces the range with one `pen.insertText`, origin `keyboard`; Backspace and Delete delete it), a composition keystroke (`isComposing`, `key === "Process"` or `keyCode === 229`) deletes the range and projects and focuses the caret's field in the same `keydown` turn so the composition starts there — except `keyCode` 229 with `key` `Unidentified`, an Android keyboard's report for every key including Backspace, which the sink leaves alone because the input that would decide it never reaches a non-editable sink (FE2), and `copy`, `cut` and `paste` reach the same transfer handlers as a field (FE2).
- S3. Every accepted authority write carries an origin from a real source: `pointer` for pointer gestures and for context-menu and drop transfers, `keyboard` for keymap commands, text input, and keyboard-initiated paste, `ime` for composition, `restore` for history restores, `programmatic` for host API calls, and `mapped` only inside `onCommit`. A write equal to the current state is not accepted, with one exception: a `restore` write claims a record that another origin holds, because the history commit maps the selection before the restore lands and the two often agree, and an unclaimed restore would not scroll. The convenience setters take an optional `origin` that defaults to `programmatic`, and no gesture, key, or transfer path in `@input/pen-dom` calls one without it; host-API forwarding and `FieldEditor.focus()` re-targeting are the listed exceptions (`scripts/selection-origin-allowlist.json`), enforced by the `pen/require-selection-origin` lint rule over `@input/pen-dom` and `@input/pen-undo` production sources. A write that coalesces under A2 keeps the record's origin, so a paste or command caret that lands where A5 already mapped it stays `mapped` with its `user` commit.
- S4. No selection code path contains `requestAnimationFrame`, `setTimeout`, `setInterval`, `setImmediate`, `requestIdleCallback`, `queueMicrotask`, a `Promise.resolve().then` deferral, an `async` function or `await`, a scheduler callback that calls an authority setter, or a retry counter. The one microtask on a selection path is R1's `pointer-settled`, which changes gesture-window state and writes nothing; a scheduler callback may call the projector (P3, scroll-into-view) but never an authority setter. Enforcement is the `no-selection-timers` lint rule (`packages/tooling/eslint-plugin/src/rules/noSelectionTimers.js`), which covers production files whose basename contains `selection` plus an explicit module list — the focus controller, offset domain, normal-position and transition modules, the three backends, the field editor, the full reconciler, the cell controller, the pointer-gesture modules, the session reconciler, the overlay controller and layer, and the React and Vue modules that activate a field after an apply — matches R1's microtask structurally rather than by waiver, treats an out-of-scope list as a scope decision rather than a waiver, and has no allowlist: every other site is a lint error. A timer on this path is evidence of a missing attach or a wrong seam, not an engine accommodation: the fix is to delete the deferral and attach the field the write is aimed at, never to add another retry. `FieldEditor.focusTextSelection` keeps its `Promise<boolean>` signature for hosts, but the write and the focus happen in the calling turn and the promise is settled when returned.
- S5. Caret positions always satisfy the normal position policy; the fuzzer asserts `nextNormalPosition` reachability for every observed record.
- S6. The `version` and `commitId` of a `SelectionRecord` never decrease.

## Retired

- I11 is retired: it confined knowledge of the empty-block `\u200B` sentinel to a summary-builder seam and an offset-domain seam, and with the sentinel removed from storage that confinement has no subject. It is superseded by I14 and by EM1–EM8; stored domain now equals logical domain, and no code should test for the character.
- O2's original justification is retired: it blamed browsers collapsing a sentinel rect. The rule stands unchanged on the `<br data-pen-empty="">` placeholder line box instead.
- The read-escalation clause once attached to reader step 5 — that a pointer proposal covering a non-text block produces a `BlockSelection` — is deleted. It contradicted T2, T3, and the N2 mixed-boundary delete; reads are never escalated by block type, and no document profile reintroduces the flip.
- The overlay caret's fixed 530ms blink cycle is retired. Pen manages only the blink phase; the cycle is supplied by the host through `--pen-editor-caret-animation`.
- The overlay caret's 500ms type-pause timer is retired, along with the React-only overlay that carried it. A keyed element restart on user-origin commits and caret moves replaces it, so no selection or overlay path holds a timer (S4).
